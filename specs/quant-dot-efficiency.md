# Spec 05：量化点积内核效率 —— 降"每元素指令数"

> 状态：**草案，待审阅**（未写任何生产代码；Stage 0 是纯测量）
> 上游基线：`5096f2a` + `c649f60` + Spec 01/02/03 叠加态，`GGML_AVX_VNNI=OFF`
> 证据：`ctest/benchmark_results.md` §22.8（方法学）、§22.9（字节真相）、§22.10（修正总表）、**§22.11（地基级更正 #2）**
> 一句话目标：让 q5_0 的实得带宽从 **28.3 GB/s 追到 q8_0 的 35.3 GB/s** ⇒ **+25%**（64.9 → 81 t/s）

---

## 1. 为什么是这条路线（以及为什么这次不一样）

### 1.1 §22.11 把靶子换了

三天来我们一直用屋顶线 `tok/s = 有效带宽 / 每 token 字节`，并据此认为"减字节就能线性提速"。
§22.11 实测推翻了它：

```
实得带宽 = t/s × decode 字节/token
f16  2.000 B/elem -> 41.8 GB/s      q4_k_m 0.562 B/elem -> 24.4 GB/s
q8_0 1.062 B/elem -> 35.3 GB/s      q3_k_l 0.430 B/elem -> 24.1 GB/s
q5_0 0.688 B/elem -> 28.3 GB/s      q2_k   0.328 B/elem -> 22.8 GB/s
q4_0 0.562 B/elem -> 27.9 GB/s
```

**带宽受限的话，所有类型应该都是同一个数。** 实测是 22.8~41.8，且随 B/elem 单调下降。
⇒ 瓶颈是**每元素的指令/吞吐成本**：字节压得越紧，每个字节要摊的解包指令越多。

⇒ **减字节不再是主杠杆，降每元素指令数才是。** 这是本 spec 与前三稿的根本区别。

### 1.2 为什么相信 35.3 GB/s 可达

q8_0 与 q5_0 走**完全相同**的 `ggml_vec_dot_*` 框架、相同的线程切分、相同的 q8_0 激活。
唯一区别是块结构：q8_0 每块 1 个 f16 scale、8-bit 直接装载；q5_0 每块要
`bytes_from_nibbles_32` + `bytes_from_bits_32` + `andnot` + `or` 才能拿到 5-bit 值。
同样的硬件、同样的框架，q8_0 多拿 25% 带宽 ⇒ 差距在内核形态，不在机器。

### 1.3 ⚠️ 我可能被证伪的地方（必须写在前面）

**§13 和 §15 都是从"我认为机制是 X"出发做优化，结果收益只有预测的 1/3 到 1/5。**
两次失败的共同点：**先把机制当成已知，再动手改代码**。

本 spec 因此**强制 Stage 0 先做判别性实验**，且 Stage 0 的任何一个结果都可以直接
改变或终止 Stage 1。若 E-1 显示"L2 常驻与 DRAM 常驻速度几乎相同"，说明纯指令瓶颈，
Stage 1 的展开才是对症的；若显示"L2 常驻快得多"，说明内存并行度仍是主因，
Stage 1 应改为预取/分块而不是展开——**那时 Stage 1 的实现要重写**。

## 2. Stage 0：判别性实验（不写生产代码，只测量）

全部用 §22.8 的方法（f16 锚点 + 交替 A/B + 摆幅 >8% 丢弃），机器独占。

### E-1（决定性）：L2 常驻 vs DRAM 常驻，`vec_dot` 微基准

新增 `ctest/vecdot_micro.c`（**仅测试用，不进 ggml 构建**）：

- 分配 A：4 MiB 权重 + 4 MiB 激活（**L2/L3 常驻**，Ultra 7 155H L3 = 24 MB）
- 分配 B：512 MiB 权重 + 激活（**必须走 DRAM**）
- 两种各跑 `ggml_vec_dot_q5_0_q8_0` / `q4_0` / `q8_0` / `f16`，元素总量相同
- 输出：`cycles/element` 与 `GB/s`

判定：

| 结果 | 含义 | Stage 1 走向 |
|---|---|---|
| B 比 A 慢 ≥2× | 内存（延迟/并行度）仍是主因 | 改预取 + 分块 |
| B 与 A 差 <1.3× | **纯指令吞吐瓶颈** | 展开 + 减指令（原计划） |
| 中间 | 两者混合 | 先做收益大的一侧，用数据定 |

**这一条决定 Stage 1 写什么。**

### E-2：线程扫描（看 E/P 核异构）

Ultra 7 155H = 6P + 8E + 2LPE（22 线程）。ggml 按行**均分**给线程，
makespan 由最慢的线程决定 ⇒ **E 核可能把整批拖到 E 核速度**。

q5_0 与 f16 各跑 `t = 1 2 4 6 8 12 16 22`，画 speed-vs-t 曲线。
若 t=6（纯 P 核）已接近 t=12，则 **`-t 6` 是零代码收益**，且 Stage 1 的收益应按
P 核吞吐估算而不是 22 线程平均。

### E-3：`--output-tensor-type` 压 lm_head（零代码，顺手做）

§22.9：lm_head 在所有量化模型里被 `llama-quant.cpp:472` 强制降级为 **Q6_K**，
占 q4_0 decode 流量的 **33%**、q2_k 的 **43%**。这是"地板"。

- `llama-quantize ... q5_0 --output-tensor-type q5_0` → lm_head 127.6 → 107.0 MB
- `llama-quantize ... q4_0 --output-tensor-type q4_0` → lm_head 127.6 → 87.5 MB
- `llama-quantize ... q4_k_m --pure` → 去掉 `ffn_down`/`attn_v` 的 Q6_K（48.1 MB）

每个都测 **速度 + PPL**（PPL 用现有 `ctest/ppl_small.txt` 语料与口径）。
按 §22.11，增益会**小于**字节减少量——这个"小于多少"本身就是 E-1 的旁证。

### E-4（可选）：4B 交叉验证

§22.6 旧数据显示"模型越大效率越高"（0.6B 56.7% → 4B 66.5%，旧口径）。
若用新口径重测仍然成立，说明**矩阵越大，每元素摊到的固定开销越少**
（每元素开销不是常数，含 per-call/per-row 成分）⇒ Stage 1 应同时考虑
**增大每次 `vec_dot` 调用的 n**（现在 0.6B 的 K=1024 只有 32 块/行，调用很短）。

## 3. Stage 1：内核改造（**在 E-1 结论出来后才动手**）

### 3.1 现状（`ggml/src/ggml-cpu/arch/x86/quants.c`）

`ggml_vec_dot_q4_0_q8_0`（:701）与 `ggml_vec_dot_q5_0_q8_0`（:1142）的 AVX2 路径
结构完全相同，**每轮只处理 1 个块（32 元素）**：

```c
__m256 acc = _mm256_setzero_ps();
for (; ib < nb; ++ib) {
    const __m256 d = _mm256_set1_ps(FP16(x[ib].d) * FP16(y[ib].d));
    __m256i qx = bytes_from_nibbles_32(x[ib].qs);      // q5_0 还要 +qh 拆包
    __m256i qy = _mm256_loadu_si256((const __m256i *)y[ib].qs);
    const __m256 q = mul_sum_i8_pairs_float(qx, qy);
    acc = _mm256_fmadd_ps(d, q, acc);                  // ← 串行浮点依赖链，4c 延迟
}
```

三个可疑点：**① 无展开**（依赖链串行）；**② 无软件预取**
（同文件的 SSSE3 分支有 `_mm_prefetch`，AVX2 分支反而没有）；**③ 每块一次
`FP16→FP32` 两次 + `set1`**。

### 3.2 改动（按 E-1 结论选一组）

**方案 A（E-1 显示纯指令瓶颈）** —— 展开 ×2 / ×4：

- 4 个独立 `__m256 acc0..3`，一次迭代吃 4 个块（`ib += 4`，尾部回落到标量循环）
- 4 条 `d` 的 `FP16→FP32` 合并为一次 `_mm256_cvtph_ps`（若可用）或至少批处理
- 保持 `mul_sum_i8_pairs_float` 不变（它是共用的算术，不许漂移，同 §13 的教训）

**方案 B（E-1 显示内存并行度瓶颈）** —— 预取 + 大步幅：

- 每次迭代对 `ib + 8`、`ib + 16` 做 `_mm_prefetch(..., _MM_HINT_T0)`
- 不展开累加器（避免改变求和顺序）

**方案 C（E-4 显示 per-call 开销显著）** —— 增大每次调用的 n：
在 `ggml_compute_forward_mul_mat` 里让量化路径一次处理更多行
（`nrc` 方向），摊薄 per-call 开销。**这条改动面最大，放最后。**

### 3.3 bit-exactness：这次不承诺

§22.7 曾写"整数累加满足结合律 ⇒ 改循环顺序仍 bit-exact"。**这句话不成立**：
每个块有自己的 scale（`x[ib].d * y[ib].d`），必须先缩放再累加，
所以累加是**浮点**的，换顺序就不再 bit-exact。

⇒ 改用 **PPL 门禁**（同 §15 的 G1）而不是 bit-exact 门禁：
PPL 相对 f16 的偏移变化 < 0.05% 绝对值。
（q5_0 当前 ΔPPL = +0.06%，本来就不为零。）

### 3.4 回滚开关

`LLAMA_DOT_UNROLL=0` 走原路径，默认 1（若验证通过）。
不得影响任何非 AVX2 路径。

## 4. 验收门禁

| # | 条件 | 阈值 |
|---|---|---|
| **G1** | q5_0 tg128 相对 q4_k_m（= 当前默认）speedup，交替 A/B 干净块 | **≥ +20%** |
| **G2** | q5_0 实得带宽 | **≥ 32 GB/s**（基线 28.3，q8_0 参照 35.3） |
| **G3** | PPL 相对改造前的变化 | **< 0.05%** 绝对值 |
| **G4** | 所有其他量化类型 + f16 | **零回归**（各类型 ×f16 比值变化 < 2%） |
| **G5** | 短上下文（ctx≤2048）与 prefill（pp512） | 无回归（> −2%） |
| **G6** | 4B 模型交叉验证 | 同向增益（方向一致即可，幅度不限） |

**G1 不达标即视为未通过**，即使 G2/G3 通过 —— 理由同 §15：
我们要的是墙钟时间，不是漂亮的中间指标。

## 5. 明确不做

- **不动 `_K` 系列内核**：§22.10 已证 `_0` 同 B/elem 快 10~19%，直接换格式更划算。
- **不动 VNNI**：`GGML_AVX_VNNI` 默认 OFF，开启后收益被噪声淹没（§22 已回滚），
  除非 E-1 的微基准能在 L2 常驻下测出明确差异，否则不再碰。
- **不重写 `mul_mat`**：§15 已证"沿 T 重写点积 = 重写 mul_mat"，成本不划算。
- **不做 1.58-bit / 新格式**：需重训。
- **不改模型结构/剪枝**：超出"反量化效率"范围。

---

## 6. 与 §18 目标口径的关系（别做无用功）

§18 的结论仍然有效：**单用户交互式创作场景下 13.8 tok/s 已快过人类阅读 2.5~3.2×，
100 tok/s 是过度目标**。本 spec 的收益（q5_0 64.9 → 81 t/s）只在**批量出稿**
场景下才有实际意义。

⇒ **开工前仍需用户确认形态**：若确认是交互式创作，本 spec 应降级为"顺手做"，
优先级排在 §18 的常驻/流式/持久化之后。
