### 关于 acceptance 的可复现性（方法论坑）

同一个 `n-max=4` 配置，污染时读到 0.494，干净时读到 0.416，且 generated 计数
不同（170 vs 190）——**即使 temperature=0，生成文本也非逐位可复现**（多线程浮点
归约顺序/batch 切分会导致 argmax 在近似并列处翻转）。所以单次 acceptance 读数
有 ±8pp 量级的波动，**不能拿单个数字下结论，必须多轮取中位数**。

### 为什么赔（时间账）

每轮 = 3 次 draft 前向 + 1 次验证：

- 无 draft：100 ms / token
- 有 draft：`3×18ms(draft) + 263ms(验证)` = 154 ms / token

真凶在验证阶段：batch 从 1 涨到 ~4，**耗时涨 2.6 倍**，几乎线性叠加。
CPU 上批量前向在时间上省不掉，投机省的是"带宽"、付的是"串行时间"。

### 硬门槛：词表必须匹配

```
draft model vocab must closely match target model to use speculation
target vocab size 59264 does not match draft vocab size 151936 (max allowed 128)
```
用 Qwen3-0.6B 猜 glm-edge-4b → 投机被**静默降级**（服务照常出结果，只是不投机）。

## 6. 批处理效率曲线 —— 投机命中在 CPU 上的"物理"与"实现"缺口

> 2026-09-26 补测。这一节推翻了"4B 不是带宽受限"的旧结论，并给出了本项目
> **唯一一个值得动代码的具体靶点**。

### 6.1 两个模型都贴在同一堵内存墙上

| 模型 | 大小 | t/s | 等效带宽 |
|---|---|---|---|
| 0.6B Q4_K_M | 456 MiB | 82.73 | 37.7 GB/s |
| 0.6B Q2_K | 326 MiB | 105.63 | 34.4 GB/s |
| qwen3-4b Q4_K_M | 2.32 GiB | 14.80 | 35.2 GB/s |
| glm-4b Q4_K_M | 2.44 GiB | 14.69 | 36.7 GB/s |

**0.6B 与 4B 的有效带宽都是 ~35-37 GB/s** —— 同为带宽受限。

### 6.2 CPU 极擅长批处理（关键实测）

**（本节初版用 llama-bench `-p N` 测的是 prefill 路径，已作废。下方为 decode 路径重测。）**

`llama-server -np N` + N 个并发请求，短 prompt（prefill 可忽略）+ 256 token 生成，
隔离出**纯 decode** 的批处理增益。target = qwen3-4b Q4_K_M，t=12：

| 并发 N | 聚合吞吐 | 相对单流 | 单请求 t/s | batch-N 前向耗时 / batch-1 |
|---|---|---|---|---|
| 1 | 13.59 t/s | 1.00× | 13.59 | 1.00× |
| 2 | 20.85 t/s | **1.53×** | 10.42 | 1.30× |
| 4 | **34.81 t/s** | **2.56×** | 8.70 | 1.56× |
| 8 | 36.63 t/s | 2.70× | 4.58 | 2.97× |

**核心事实：batch=4 前向耗时是 batch=1 的 1.56 倍，但读的字节完全一样（权重只读一遍）。**
多出来的 0.56 倍不是带宽，是算力——batch=1 时算术强度约 2 FLOP/byte（带宽受限），
batch=4 时同样字节要做 4 倍 FLOP，算术强度升到约 8，向算力受限移动。

**推论（推翻了本项目此前"带宽是唯一瓶颈"的单货币模型）：**
"省带宽"只在 batch=1 的世界里等价于"省时间"。投机恰恰把 batch 从 1 变成 N+1，
**自己把自己推出了带宽墙的适用范围。**

### 6.3 由此推出的投机理论收益 vs 实测（已修正）

上一版公式 `(N·d + b) / (N+1)` 的分母假设了 **100% 命中**，这是错的。
正确分母是**实际收下的 token 数** `A = acceptance·N + 1`。

n_max=4 的三层口径：

| 口径 | 每 token 读/花 | 相对基线 |
|---|---|---|
| A. `(4d+b)/5`，假设 5 个全收下（**错**） | 887 MB | 省 2.8× |
| B. `(4d+b)/2.66`，实际只收下 2.66 个（**字节口径真实值**） | 1668 MB | 省 **1.50×** |
| C. 再乘 batch 时间成本 `C(5)=2.01×`（**时间口径真实值**） | — | 省 **1.00×** |

**"省 2.5 倍带宽"这个说法本身站不住；真实是 1.5 倍，且兑换成时间后等于零。**

理想实现（零上游开销）下的完整时间账，单位 = 一次 batch-1 target 前向
（`r = 0.164` 为实测 0.6B/4B batch-1 decode 耗时比）：

| n_max | accept | 收下 token | draft 前向 | verify | 合计 | 理想加速 | 实测 | 实现开销 |
|---|---|---|---|---|---|---|---|---|
| 1 | 0.70* | 1.70 | 0.16 | 1.30 | 1.46 | **1.16×** | 未测 | — |
| 2 | 0.58* | 2.16 | 0.33 | 1.45 | 1.78 | **1.21×** | 未测 | — |
| 3 | 0.50* | 2.50 | 0.49 | 1.56 | 2.05 | **1.22×** | 未测 | — |
| 4 | 0.416 | 2.66 | 0.66 | 2.01 | 2.67 | **1.00×** | 0.69× | **1.45×** |
| 6 | 0.213 | 2.28 | 0.98 | 2.70 | 3.68 | 0.62× | 0.48× | 1.29× |
| 8 | 0.301 | 3.41 | 1.31 | ~3.3 | 4.61 | 0.74× | 0.45× | 1.64× |

\* n_max=1/2/3 的 accept 为外推值，未实测。

**修正后的结论（比上一版悲观得多）：**
- 修掉上游 re-eval 开销，n_max=4 最多回到**打平**（1.00×），不是上一版说的 1.75×。
- 唯一可能真赚的是 n_max=1~3（理想 1.16~1.22×），**这三档从未测过**；
  扣掉约 1.4× 实现开销后仍是亏损。
- 盈亏平衡命中率 27.7% 那个数字作废——它同样建立在 100% 命中的分母上。

### 6.4 上游自己承认了这笔开销

`tools/server/server-context.cpp:3057` 与 `:3741`：

```
// TODO: avoid restoring the draft context and re-evaluating the drafted tokens
//       when not needed [TAG_SPEC_AVOID_DRAFT_REEVAL]
//       for now, always re-evaluate for simplicity
//       ref: https://github.com/ggml-org/llama.cpp/pull/22728#issuecomment-4400925384
```

每轮都要**恢复 draft 上下文 + 重算已 draft 的 token**，且两份 checkpoint
（tgt/dft）都要 save/load。这就是那 2.5 倍的去向。

### 6.5 投机的隐藏成本：把开销从生成端搬到 prefill 端

1436-token prompt 下的 prompt eval 耗时：

| | 无 draft | 有 draft | 差 |
|---|---|---|---|
| prompt eval | 25.03 s | 34.47 s | **+9.44 s（+38%）** |

draft 模型必须把 prompt 也吃一遍才有自己的 KV 状态。这是**每请求的固定成本**，
长 prompt + 短生成时直接致命，只有生成足够长才摊得掉。
（本项目的 A/B 用 server 的 prompt 缓存，取第 3 次请求读数，已规避此成本——
所以 11.69 vs 8.10 是干净的纯生成对比。）

### 6.6 撤回：投机的真实代价不是内存容量，是带宽

此前列出的一条"优势/代价"——**"多付 0.5GB 内存"——予以撤回**。

本机实测：物理内存 31.5 GB，target 2.5GB + draft 0.48GB = 3.0GB，占用 9.5%；
多出的 0.48GB 仅占总量 1.5%。**内存容量在任何测过的配置下都不构成约束**，
那条是从"边缘设备内存紧张"的通用叙事里借来的，本项目零数据支持。

修正后的准确说法：投机不是"拿内存换带宽"，而是**拿带宽换带宽**。

draft 模型每轮那 N 次前向本身就在消耗本机唯一稀缺的资源（~36 GB/s 带宽），
而且用的是最差的消费方式——**batch=1，正是这台机器效率最低的形态**（见 6.2：
batch=1 是带宽受限、算术强度最低的点）。在 d/b = 0.19 这组参数下这笔交易是亏的。

要让交易划算，需要 d/b 显著更小（例：d/b = 0.05 时理想约 1.4×），
即 target 更大或 draft 更小——本项目选的 4B + 0.6B 组合方向不对。

### 6.7 真正的大赢家：并发批处理，不是投机

同一个机制（把 batch 从 1 变大），两条路线的收益天差地别：

| 路线 | batch 来源 | 命中率 | 实测聚合增益 |
|---|---|---|---|
| 投机命中（draft model） | 人工猜 N 个 token | 41.6% | **0.69×（亏损）** |
| 并发连续批处理（`-np 4`） | 4 个真实并发请求 | **100%** | **2.56×** |

并发批处理拿到的是同一份批处理红利，但**不用付 acceptance 的税**——
每个 batch 行都产出一个真实 token，没有白猜的。

**结论：在 CPU 上想吃批处理红利，正确做法是连续批处理 / 提高并发，不是投机解码。**
这也重新回答了项目最初那个一直悬着的问题——单用户延迟 vs 多用户吞吐：
吞吐侧答案已经明确（np=4 → 2.56×）；单流延迟侧，投机这条路基本封死。

## 7. 其他结论

- **BitNet b1.58 这条路是死的**：新版 ggml 已移除 `I2_S` 量化类型（CPU 后端无三元
  矩阵乘内核，仅 cuda/sycl 保留），且转换就失败（`ffn_sub_norm` 张量无法映射）。
- **KV 缓存量化不是提速手段**，是省内存手段：每 token 都要反量化，长上下文下 q4_0
  比 f16 慢约 37%。
- `llama-cli` 走 server 后端，投机支持不完整，测投机必须用 `llama-server` + curl。
- curl 访问 localhost 必须加 `--noproxy '*'`，否则被代理拦截返回 502。

## 8. 单用户场景：上下文长度才是第一杀手（此前完全没测）

前提：本地部署、单用户、无并发 → 并发批处理出局，只剩"每 token 读多少字节"这一条路。
此前所有测量都在**空上下文**下做的，因此漏掉了单用户场景最大的变量。

### 8.1 Qwen3-0.6B 的 KV cache 体积（f16，112 KiB/token）

| 上下文 | 1K | 4K | 8K | 32K |
|---|---|---|---|---|
| KV 体积 | 112 MiB | 448 MiB | 917 MiB | 3584 MiB |

模型本体只有 325 MiB。**ctx 超过约 3000 后，KV 读取量就超过模型权重本身。**

### 8.2 上下文长度 → decode 速度（Q2_K 325MB，t=12，`llama-cli` 实测）

注意：`llama-bench` 的 tg 测量**不带 prompt 上下文**（4 个 `-p` 值只产出 1 行 tg128），
用它测上下文影响会得出"无影响"的错误结论。必须用 `llama-cli -f <长prompt>` 测。

| 上下文 | 64 | 256 | 512 | 1024 | 2048 | 4096 | 8192 |
|---|---|---|---|---|---|---|---|
| fa=1（默认 auto） | 92.6 | 84.4 | 78.7 | 64.1 | 46.2 | 25.0 | **12.3** |
| **fa=0** | 82.1 | 75.3 | 69.3 | 62.2 | **52.2** | **36.4** | **23.5** |

**从 ctx 64 到 8192，速度掉 3.7 倍（fa=0）到 7.5 倍（fa=1）。**
单用户本地部署的真正瓶颈是累积的对话历史，不是模型大小。

### 8.3 实用发现：flash attention 在长上下文是负收益（可复现）

交叉点在 **ctx ≈ 1500–2000**。三轮复测稳定：

| 上下文 | fa=1 | fa=0 | fa=0 增益 |
|---|---|---|---|
| 64 | 92.6 | 82.1 | −11%（fa=1 胜） |
| 512 | 78.7 | 69.3 | −12%（fa=1 胜） |
| 1024 | 64.1 | 62.2 | −3%（基本持平） |
| 2048 | 46.2 | 52.2 | **+13%** |
| 4096 | 24.7~25.5 | 35.9~37.0 | **+44%** |
| 8192 | 12.3 | 23.5 | **+91%** |

**llama.cpp 的 `-fa auto` 在长上下文选错了**——CPU 的 flash attention 内核随上下文
退化极快，legacy 路径反而更好。这是本项目**第一个有数据指认的具体魔改靶点**：
把 auto 的判定改成按上下文长度切换，一行启发式即可，收益最高 91%。

### 8.4 KV 量化：~~确认无效~~ **结论作废，见 §10.2**（实测污染）

~~| KV 类型 | ctx 4096 | ctx 8192 |~~
~~| f16 | **26.2** | **13.1** |~~
~~| q8_0 | 18.6 | 10.6 |~~
~~| q4_0 | 22.0 | 13.0 |~~

**作废原因**：`llama-context.cpp:3819` 规定**量化 V 会强制开启 flash attention**。
所以上表的 q8_0 / q4_0 两行跑的是 FA 路径，而 f16 那行跑的是 legacy 路径——
测的不是"KV 类型"的差异，而是"FA vs legacy"的差异（而 FA 在长上下文本来就慢一半）。
结论"KV 量化在 CPU 上无效"是**测量污染造成的假象**，已在 §10.2 用干净对照推翻。

### 8.5 单用户提速手段排序（按已验证收益）

1. **控制上下文长度**（最大杠杆，3.7~7.5 倍）——限制 `-c`、定期裁剪/摘要历史
2. **长上下文关 flash attention**（+13% ~ +91%，已复现）
3. **降比特量化**（已验证：Q4 82.7 → Q2_K 105.6）
4. **长上下文下量化 K cache**（+13%，§10.2；§8.4 的旧结论已作废）
5. 架构选择（结构性）：KV head 更少的 GQA、**MLA（DeepSeek，KV 压一个数量级）**、
   滑动窗口注意力
6. 未测：CPU 亲和性（Meteor Lake 6P+8E，`-t 12` 混用 P/E 核）、mlock、大页、IQ 系列

**注意：本节的收益排序建立在短上下文（ctx ≤ 1024）基准上。真实场景是长上下文，
权重占比会坍塌到 27% 以下、优化优先级反转，见 §10。**

**单用户 100 t/s 的成立条件：Q2_K + 上下文控制在 ~1000 以内 + fa=1。上下文一长就没救。**

## 9. 第一个代码级魔改：让 `-fa auto` 感知上下文长度（已实现并验证）

spec：`<PROJECT_ROOT>/specs/fa-auto-adaptive.md`
构建：llama.cpp 本地 fork，基线 `5096f2a`+`c649f60`，Ninja+MSVC 编译通过（153/153）。

### 9.1 上游行为：`auto` 只问后端「你支持吗」，从不问「现在多长」

- `common/arg.cpp:1751` 解析 `-fa [on|off|auto]`
- `src/llama-context.cpp:230` → `cparams.flash_attn = (type != DISABLED)`
- `src/llama-context.cpp:556` → 建上下文时 probe **一次**「后端能否跑 flash attention」
  （CPU 答「能」），之后 `auto_fa = false`，永不重判
- `src/llama-graph.cpp:2635` → 此后每个 graph 无条件用这个布尔值

即 **CPU 上 `auto` ≡ `on`**，且完全静态。§8.3 那 13%~91% 必须用户手动 `-fa 0` 才拿得到。

### 9.2 关键否决：不能「每步动态切换」

原本想每个 decode step 按当前 `n_kv` 选路径。实现中发现被架构否决：

KV cache 的 **V 张量布局在建 cache 时就固定**（`llama-model.cpp` 十余处
`new llama_kv_cache(..., !cparams.flash_attn /* v_trans */, ...)`）。
同一份 cache 无法同时高效服务两条路，走「错」的那条每步都要整块转置 V
（`build_attn_mha()`：`if (!v_trans) { v = ggml_cont(ggml_transpose(v)); }`，
上游注释 *"note: avoid this branch"*）。

| 场景 | 每 token 额外 V 转置流量 | 对比模型本体 325 MiB |
|---|---|---|
| ctx 1024 | ≈ 114 MiB（读+写） | +35% → 吃掉 FA 仅 +11% 的优势 |
| ctx 8192 | ≈ 940 MiB | 比读整个模型还多 3 倍 |

两个方向都净亏 → **必须在建 KV cache 之前定下来**，即按启动期已知的 `n_ctx` 判定。
（真正的动态方案需要 V 双布局，内存 +50%，列为后续方向。）

### 9.3 实现

判定插入点：`llama-context.cpp`，`cparams.n_ctx` 定稿之后、KV cache 创建（:403）之前。

```cpp
if (cparams.auto_fa && !cparams.fa_adaptive && params.fa_kv_threshold > 0 &&
    cparams.n_ctx > (uint32_t) params.fa_kv_threshold) {
    cparams.flash_attn = false;   // 同时决定 V 布局 = 转置（legacy 友好）
    cparams.auto_fa    = false;
}
```

配套改动：`llama.h` 新增 `fa_kv_threshold` / `fa_max_tokens`；`llama-cparams.h` 新增
`llama_fa_enabled()` 作为唯一判定真源（mask 类型、`use_flash_attn`、dsv4、no_cache、
cross 五处统一走它）；`can_reuse_kq_mask()` 增加 mask 类型检查；
CLI 新增 `-fakv N` / `-fatok N`；`LLAMA_FA_DYNAMIC=1` 保留实验性每步切换。

`-fa on` / `-fa off` 行为完全不变；`-fakv 0` 退回上游行为。

### 9.4 实测结果（Q2_K 325MB，t=12，`llama-cli -f` 生成 128 token）

#### A. 「按需设 -c」场景（`-c` = prompt 长度的 2 倍，默认阈值 2048）

| prompt | -c | **auto（新）** | `-fa 1`（旧行为） | `-fa 0` | 新 vs 旧 |
|---|---|---|---|---|---|
| 64 | 512 | **97.1** | 95.6 | 81.6 | +1.6% |
| 256 | 512 | **83.6** | 82.6 | 78.3 | +1.2% |
| 512 | 1024 | 77.5 | 78.1 | 72.7 | −0.8%（噪声内） |
| 1024 | 2048 | **66.3** | 65.7 | 64.1 | +0.9% |
| 2048 | 4096 | **54.2** | 46.2 | 52.3 | **+17%** |
| 4096 | 8192 | **36.6** | 25.3 | 36.8 | **+45%** |
| 8192 | 16384 | **23.5** | 12.4 | 23.7 | **+90%** |

**每个上下文长度都拿到了两条路中的较优者**，长上下文相对旧默认提速 17%~90%，
短上下文零损失（差值在 ±2% 噪声内）。

阈值对比（prompt=1024 / -c 2048 那一行）：阈值 1024 → legacy 63.4；
**阈值 2048 → FA 66.3（+4.6%）且命中实际最优**。默认取 2048。

#### B. 已知边界：`-c` 设得远大于实际用量时

固定 `-c 16384`：

| prompt | auto（新） | `-fa 1` | `-fa 0` | 新 vs 旧 |
|---|---|---|---|---|
| 64 | 80.2 | 94.7 | 80.9 | **−15%**（误判：n_ctx 大但实际只用 64） |

判定只能用启动期可得的 `n_ctx`（上限），不知道实际会聊多长。

规避：按真实需要设 `-c`，或明确知道是短对话时用 `-fakv 0`。

### 9.5 副作用

FA 与 legacy 数值路径不同，切换后相同 prompt 可能产出不同 token（速度换确定性）。
用 `-fa 0` / `-fa 1` 可固定路径。

### 9.6 下一步

真正消除 B 组的误判需要**按当前 KV 长度动态切换**，即让 KV cache 同时维护
转置与非转置两份 V（decode 每 token 多写一次 V，写入量 ~2 KiB×层数，可忽略；
代价是 V 缓存内存翻倍 → KV 总量 +50%）。这是本项目下一个值得做的靶点。

## 10. 真实场景 = 长上下文（8192+）：带宽墙与可达上限

用户在实际使用中观察到的 5~30 tok/s，对应的是**长上下文档位**，
与前面 §1-§7 的短上下文基准（ctx 64 → 105 tok/s）不是同一个世界。

### 10.1 带宽屋顶线：实测已经贴住墙

每生成一个 token，必须读：**模型权重（固定）+ 整块 KV cache（随 ctx 线性增长）**。

```
tok/s = BW / (W + ctx × kv_per_token)
```

Qwen3 架构的 KV 字节/token（f16）= `n_layer × 2(K,V) × n_kv_head × head_dim × 2B`：

| 模型 | 权重 | KV/token | KV 追平权重的 ctx |
|---|---|---|---|
| Qwen3-0.6B Q2_K | 325 MiB | 112 KiB（28层×8头×128维） | ~2900 |
| Qwen3-4B Q4_K_M | 2272 MiB | 144 KiB（36层×8头×128维） | ~16000 |

本机会话实测有效带宽 **≈31 GB/s**（由各 ctx 数据点反推一致：ctx64 33.8、1024 30.4、
2048 31.2、4096 29.7、8192 31.1 GB/s）。屋顶线预测 vs 实测：

| ctx | 0.6B Q2_K 预测 | 0.6B 实测 | 达成率 | 4B Q4 预测 | 4B 实测 |
|---|---|---|---|---|---|
| 512 | 77.6 | 77.5 | 100% | 11.2 | — |
| 1024 | 67.7 | 66.3 | 98% | 10.9 | — |
| 2048 | 53.9 | 54.2 | 100% | 10.4 | — |
| 4096 | 38.2 | 36.6 | 96% | 9.4 | — |
| 8192 | 24.2 | 23.5 | 97% | 8.0 | 7.2 (90%) |
| 16384 | 14.0 | — | | 6.1 | — |
| 32768 | 7.6 | — | | 4.1 | — |

**结论：实测已达带宽屋顶线的 90~100%。在长上下文区间，"引擎层优化"几乎没有剩余空间。**
要更快只能**减少每 token 必须读的字节数**，没有第二条路。
（算力侧佐证：ctx 8192 时注意力约 1.9 GFLOP/token × 23.5 tok/s ≈ 45 GFLOPS，
而 155H 12 线程 FP32 峰值约 400+ GFLOPS → 算力只用了 ~10%，确属带宽受限。）

### 10.2 KV 量化：污染源排除后是**真的有效**

关键发现：`llama-context.cpp:3819` 只禁止**量化 V**走 legacy 路径，
**量化 K 不受限制**。所以 `-ctk q8_0 -ctv f16` 可以在 legacy 路径下省掉 K 的字节。

ctx=8192，t=12，生成 128 token：

| 配置 | Qwen3-0.6B Q2_K | Qwen3-4B Q4_K_M |
|---|---|---|
| K=f16 V=f16 + `-fa 1`（**上游默认行为**） | 12.3 | 5.1 |
| K=f16 V=f16 + 新自适应判定（legacy） | 23.5 | 7.2 |
| K=**q8_0** V=f16（legacy） | 25.7 / 25.1 / 24.9 | 7.5 |
| K=**q4_0** V=f16（legacy） | **26.6** | 7.5 |
| K=q8_0 V=q8_0（**被强制回 FA**） | 14.3 | — |

- 0.6B：K 量化 q4_0 在 legacy 上再 **+13%**；合计 vs 上游默认 **12.3 → 26.6 = 2.16×**
- 4B：只 **+4%**。因为 4B@8192 时权重仍占 69%，KV 只占 31% → 省 KV 收益被稀释。
- 反例确认：一旦 V 被量化（触发强制 FA），14.3 反而远低于 23.5 —— 这就是 §8.4 假象的来源。

### 10.3 权重占比随上下文坍塌 → 优化优先级反转

| ctx | 0.6B Q2_K 权重占比 | 4B Q4 权重占比 |
|---|---|---|
| 512 | 85% | 97% |
| 2048 | 59% | 90% |
| 4096 | 42% | 82% |
| 8192 | **27%** | 69% |
| 32768 | **8%** | 36% |

- **短上下文**：权重主导 → 砸权重量化（Q4 82.7 → Q2_K 105.6）
- **长上下文（真实场景）**：KV 主导 → 权重量化收益塌到 1/3 以下，必须砸 KV

### 10.4 剩余可挖的靶点（按潜在收益排序，均为"减字节"）

1. **让 legacy 路径支持量化 V**（现被硬禁，理由是 KV cache 建缓存时按
   `v_trans = !flash_attn` 固定 V 布局、量化张量给不出 legacy 需要的转置视图）。
   屋顶线估算（0.6B@8192）：K+V 都 q8_0 → 823 MiB/token → 35.9 tok/s，
   对比当前 26.6 **潜在 +35%**；q4_0 更激进但质量风险大。这是最具体的下一个魔改点。
2. **稀疏注意力**（唯一能 >2× 的）。ctx 8192 只 attend 2048 个 token：
   0.6B KV 939→235 MiB → 屋顶线 **52.8 tok/s（2.1×）**；扣掉近似检索开销仍 ~1.9×。
   收益正比于 KV 占比 → **小模型+长上下文受益最大，大模型+中等上下文受益小**（4B 仅 +50%）。
   参考思路：Double Sparsity（用 K 的少量通道做廉价打分，只取 top-k 全量）。
3. **换架构**：MQA / MLA。0.6B 的 112 KiB/token 偏肥；MLA 同规模可降到 ~30 KiB/token 量级。
4. **上下文管理**（有损）：滑窗 / 淘汰 / 摘要。0.6B 从 8192 砍到 2048 → 54 tok/s（2.3×）。
5. **硬件**：内存带宽是硬墙，本机有效 ~31 GB/s。换更高带宽的内存配置直接等比提速。

### 10.5 目标必须按上下文重新定义

**100 tok/s @ ctx 8192 在本机物理上不可能**：100 tok/s 意味着每 token 只能读 ~310 MB，
光 Q2_K 权重就 325 MiB。可达上限（屋顶线）见 §10.1 表格。

- ctx ≤ 512：100 tok/s 可达（已达 77.5，靠 Q2_K + 短上下文）
- ctx 8192：0.6B 上限 ~24，4B 上限 ~8 —— 与用户实测的 5~30 tok/s 完全吻合
- ctx 32768：0.6B 上限 ~7.6，4B 上限 ~4.1

### 10.6 投机命中：在长上下文**首次转正**（短上下文的"无效"结论同样作废）

| 配置（ctx=8192，t=12，n=128） | Qwen3-0.6B Q2_K | Qwen3-4B Q4_K_M |
|---|---|---|
| 基线（无投机） | 23.4 / 23.6 | 7.2 |
| `--spec-type ngram-mod` | 33.2 / 32.7 / 26.0 | 7.0 |
| `--spec-type ngram-map-k` | 30.6 | — |
| `-ctk q4_0 -ctv f16`（K 量化） | 26.6 / 25.6 | 7.5 |
| ngram-mod **+** K 量化 | 26.5 / 26.2 / 25.8 | — |

- **ngram 自投机在长上下文有效**（+11% ~ +42%），此前在短上下文测出的"持平/更慢"作废。
  机理：ngram 自投机是在**已有上下文里找匹配的 n-gram**——上下文越长，可匹配的材料越多，
  命中率越高。短上下文根本没东西可匹配，所以无效。这与"带宽是否被摊薄"无关。
- **方差很大**：同一配置 26.0 ~ 33.2（命中率随生成内容漂移）。需要更多轮次才能定论。
- **与 K 量化不叠加**：两者各自 ~+11~30%，合起来仍落在 26 左右。原因待查。
- **4B 无收益**（7.0 vs 7.2）。4B 的输出重复度低，n-gram 命中不上；
  且 4B@8192 权重占 69%，摊薄 KV 的收益本就有限。
- **draft model 投机在长上下文是结构性必亏**：draft 自己也有同长度 KV。
  0.6B draft @8192 每步读 325+917=1242 MiB，4B target 3712 MiB；
  按 N=4、接受 2 个算：(3712 + 4×1242)/2 = 4340 MiB/token > 3712 基线 → 净亏 ~17%。
  只有**不产生额外 KV** 的自投机（ngram）才可能赚。

### 10.7 当前最优组合（0.6B Q2_K，ctx 8192）

| 阶段 | 配置 | tok/s | 累计 |
|---|---|---|---|
| 上游默认 | `-fa auto`（=FA）+ KV f16 | 12.3 | 1.00× |
| + 自适应 FA 判定 | 自动切 legacy | 23.5 | 1.91× |
| + K 量化 | `-ctk q4_0 -ctv f16` | 26.1~26.6 | 2.12× |
| + ngram 投机（未稳定叠加） | `--spec-type ngram-mod` | 26~33 | 最高 2.7× |

**全部是配置/开关层面的收益，尚未动到内核。** 代码改动只有 §9 那一处 FA 判定。

## 11. 解除"量化 V 硬禁"：实测结论（-- 这个 +35% 拿不到）

### 11.1 做了什么

上游在两处禁止量化 V 走 legacy 路径：
- `llama-context.cpp:3819`：`ggml_is_quantized(type_v) && fa != ENABLED` → **强制提升为 ENABLED**
- `llama-context.cpp:499`：`!flash_attn && quantized type_v` → 直接抛异常

两处都用环境变量 `LLAMA_QV_LEGACY=1` 旁路掉（默认关闭，行为不变），重新编译后测试。

### 11.2 结果：不崩，但输出是错的

Qwen3-0.6B Q2_K，`--temp 0`，同一 prompt：

| 配置 | 生成内容 |
|---|---|
| K=f16 V=f16（合法） | `Okay, let's see. So I need to figure out why the answer is...` |
| K=q8_0 V=f16（合法） | `Okay, let's see. So I need to find the answer...` |
| K=f16 V=**q8_0** | `以下 searchData searchData searchData ...`（退化重复） |
| K=**q4_0** V=**q4_0** | 同上，完全一样的垃圾 |

q8_0 / q4_0 产生**逐字相同**的垃圾 → 不是量化误差，是**地址算错了**。

### 11.3 根因（不是"没实现"，是数据模型不允许）

`llama-kv-cache.cpp:1299-1315` 的 `get_v()`：

- `v_trans=false`（FA 路径）→ 视图 `ne=[n_embd_head_v, n_head_kv, n_kv, ns]`，**dim 连续**
- `v_trans=true`（legacy 路径）→ 视图 `ne=[n_kv, n_head_kv, n_embd_head_v, ns]`，
  且 `nb[1]=row_size(kv_size*n_embd_head_v)`、`nb[2]=row_size(kv_size)`，
  **最内层维度是 token、元素步长 = 1**

而 `ggml_mul_mat` 的 src0 要求**被收缩的那一维连续且块对齐**。legacy 的 PV 计算
`out[d] = Σ_t attn[t]·V[t,d]` 收缩的是 token 维，所以 V 必须以 token 为最内层连续维。
量化类型是块结构（q8_0：32 元素 + 2 字节 scale = 34 字节/块），`nb[0]` 会取到
`ggml_type_size(type)` = 34 字节/块，而正确的元素步长应是 34/32 字节 → **整套寻址错位**。

**结论：上游这个禁令是正当的。量化 V 与 legacy 注意力路径在 ggml 的张量模型下不兼容。**

### 11.4 那个 +35% 到底有多大（违法配置的速度，仅供估价）

ctx=8192，t=12，n=128：

| 配置 | tok/s | 正确性 |
|---|---|---|
| K=q8_0 V=f16（合法，当前最优） | 25.6 | 正确 |
| K=q8_0 V=q8_0（**违法**） | 31.2 | **错误** |
| K=q4_0 V=q4_0（**违法**） | 34.2 | **错误** |

与 §10.4 的屋顶线预测（K+V q8_0 → 35.9）对比，实测 31.2 = 87%，缺口是反量化开销，
和 K 侧观察到的比例一致。**收益是真的，但必须由合法实现来兑现。**

### 11.5 兑现它的两条路（成本差异巨大）

**路 A：改 V cache 的存储布局**（正解，但工作量大）
让 V 以 **token 维连续**存储（`ne=[n_kv, n_head_kv, n_embd_head_v]`），
并**沿 token 维分块量化**（每 32 个连续 token 为一块）。这样 `mul_mat` 的收缩维连续且块对齐，
legacy 路径可直接吃量化 V。
代价：写入变成分块 staging（32 token 的 f16 暂存约 1.8 MiB，满了再量化落盘）；
质量风险：沿序列维量化 vs 常规沿特征维量化，需实测 PPL 验证。

**路 B：先查清 FA 为什么在长上下文慢 2 倍**（推荐先做，性价比高得多）
FA 路径**本来就支持量化 V**。如果 FA 能追平 legacy，量化 V 立刻可用且**零布局改动**。
已知事实：ctx 8192 时 FA 12.3 vs legacy 23.5（**-48%**），而两者读的字节数完全一样
→ FA 的 CPU 实现有问题（当时怀疑是线程划分 / dequant 到临时缓冲 / softmax 未向量化）。
**这是比改 V 布局更值得先做的靶点。**

> **已查清，见 §12**：上面三个猜测**全错**。真正原因是 FA 的 decode 内核把 q 头放在外层、
> KV 放在内层，导致同一 kv 头的 K/V 被组内每个 q 头各读一遍 → KV 流量 × GQA 比。
> 且**修复方案是 bit-exact 的**（不改变每个 q 头的运算顺序），无需 PPL 验证。

### 11.6 副产品与勘误

- ~~perplexity segfault~~ **勘误（2026-09-27）：perplexity 根本没坏**。exit 139 的根因是
  build/bin 里 2025-09-25 编译的 `llama-perplexity-impl.dll` 是残次构建产物（exe 只是薄壳，

  **→ 本机客观质量门恢复，非 bit-exact 改动可以用 PPL 验收，§13"没有 PPL 手段"的前提作废。**

## 12. FA 在长上下文慢 2 倍：根因定位（已查清）

### 12.1 先确认走的是哪条内核路径

`ggml/src/ggml-cpu/ops.cpp:9261`：

```cpp
const bool use_split_kv_path = !use_ref && (neq1 == 1 && neq3 == 1) && kv_is_f32_or_f16
                               && (k->type == v->type) && q->type == GGML_TYPE_F32 && nek1 >= 512;
```

`llama-graph.cpp:2633` 在调用前对 q/k/v 做了 `ggml_permute(0,2,1,3)`，所以传进来的张量是
`k: ne=[head_dim, n_kv, n_head_kv, 1]` → **`nek1 == ctx`**。因此：

- **ctx ≥ 512 的 decode 走 `use_split_kv_path`**（按 KV 分块并行，n_chunks = nth）
- ctx < 512 或 prompt 阶段走另一条（按 q 行分块；prompt 时 `neq1 >= Q_TILE_SZ` 会走
  `ggml_compute_forward_flash_attn_ext_tiled`，那个内核有 K/V 复用，**但 decode 永远用不上**）

**关键结构**（`ops.cpp:9277`）：

```cpp
const int64_t ic_start = ith * chunk_size;              // 线程按 KV 分块
for (int64_t q_head = 0; q_head < neq2; q_head++)       // 每个线程遍历【全部】q 头
    one_chunk(..., q_head, q_head+1, ic_start, ic_end, ...);
```

而 `one_chunk`（`:8698`）内部是：

```cpp
for (ir = q rows) {            // q 头在外
    for (ic = n_kv) {          // KV 在内
        k_data = k->data + ic*nbk1 + ik2*nbk2;   // ik2 = q_head / (n_q_head/n_kv_head)
        ...
    }
}
```

### 12.2 根因：每个 kv 头的 K/V 被组内每个 q 头各读一遍

`rk2 = neq2/nek2` = 每个 kv 头服务的 q 头数（= GQA 比）。
`ik2 = iq2 / rk2` → **q 头 0 和 q 头 1 读的是同一个 kv 头 0 的同一段 K/V**，但它们在两次独立的
内层扫描里各读了一遍。

于是每 token 的 KV 流量 = 名义值 × **GQA 比**：
- Qwen3-0.6B：16 Q / 8 KV → **α = 2**
- Qwen3-4B、glm-edge-4b：32/8、24/6 → **α = 4**

而 legacy 路径是两次 `mul_mat`（K^T·q 读一遍 K，V·att 读一遍 V）→ **α = 1 恒成立**。
这就是"两者读的字节数完全一样"这个旧假设错在哪：**它们并不一样，FA 多读了 (GQA比 − 1) 倍 KV。**

### 12.3 实测证据

**α 定义**：`bytes/token = W + α × ctx × kv_per_token`；用同线程数下的 legacy（α≡1）当带宽基准，
消除"线程数变化导致有效带宽变化"的干扰。

**(a) α 随 ctx 增长**（0.6B Q2_K，t=12）：

| ctx | legacy | FA | FA/legacy | 反推 α |
|---|---|---|---|---|
| 512 | 69.3 | 78.7 | 1.14 | ~1（KV 项太小，被噪声淹没） |
| 1024 | 62.2 | 64.1 | 1.03 | 1.52 |
| 2048 | 52.2 | 46.2 | 0.89 | 1.62 |
| 4096 | 36.4 | 25.0 | 0.69 | 2.11 |
| 8192 | 23.5 | 12.3 | 0.52 | **2.52** |

**(b) α 随线程数下降**（ctx=8192，n=96；每线程 KV 块 = ctx/nth × 4096 B）：

| t | FA | legacy | FA/legacy | 反推 α | 每线程 KV 块 |
|---|---|---|---|---|---|
| 4 | 6.8 | 16.4 | 0.41 | 2.91 | 8.4 MB |
| 8 | 9.8 | 19.6 | 0.50 | 2.35 | 4.2 MB |
| 12 | 12.6 | 23.6 | 0.53 | 2.18 | 2.8 MB |
| 16 | 13.0 | 22.3 | 0.58 | 1.97 | 2.0 MB |
| 20 | 12.6 | 20.1 | 0.63 | 1.81 | 1.6 MB |
| 22 | 12.7 | 19.9 | 0.64 | **1.77** | 1.5 MB |

FA 的线程扩展性（t=4→16 提速 **1.91×**）明显强于 legacy（**1.36×**）——这本身就是
"FA 的代价与每线程 KV 块大小相关、而 legacy 与它无关"的信号。

**(c) 小 ctx 对照**（ctx=512，每线程 KV 块 175 KB ≪ L2）：FA/legacy = 0.90 / 1.06 / 1.05 / 1.14
（t=4/8/12/16）。**基本持平**，绝对差仅 ±10%——说明此时**重读代价被缓存吸收了**。
对比 ctx=8192 的 0.52，差值随 ctx 单调放大 → 代价确实来自 KV 项。

**(d) 跨模型**：4B（GQA 比 4）@8192 FA=5.1 → 反推 α ≈ **3.43**。
（该数不可靠：4B 的 KV 只占 35% 流量，α 对误差极敏感；仅作趋势参考。）

### 12.4 为什么"靠缓存吸收"救不了长上下文

α 从 2.91 降到 1.77 说明缓存**能**吸收一部分重读（同一 kv 头的两个 q 头在循环里相邻，
时间局部性其实很好）。但：

- 要让重读完全命中 L2，需要每线程 KV 块 ≪ 2 MB → ctx 8192 时需要 **nth ≫ 22**
- 而 legacy 在 t > 16 已开始退化（t=12→23.6，t=20→20.1，t=22→19.9）
- 本机 L2 还要被超线程兄弟 / 4 个 E 核共享，实际可用远小于标称 2 MB

**结论：调线程数只能把 α 从 2.2 压到 1.8，救不回来。必须改算法。**

### 12.5 修复方案：按 kv 头分组，K/V 加载一次喂给组内全部 q 头

把 split-KV decode 路径的循环顺序从

```
for q_head { for ic { 读 K/V，算 } }                     // 现状：KV 读 GQA 比次
```

改成

```
for kv_head g { for ic { 读 K[g][ic], V[g][ic] 一次；
                         for j in 组内 q 头 { s = dot(K, Q[g*rk2+j]); 在线 softmax 累加 } } }
```

- KV 流量 α: GQA 比 → **1**
- 同时存活的累加器只有 rk2 个（2~8）× DV，栈上小数组足够，无需改 wdata 预算
- **bit-exact**：对每个 q 头而言 `ic` 的遍历顺序不变，M/S/VKQ 的更新顺序完全不变
  → **结果与现状逐位相同**，不需要 PPL/质量验证（这点很重要，本机 `llama-perplexity` 是坏的）
- partials 布局 `[q_head][kv_chunk][M,S,VKQ]` 不变 → reduce 阶段零改动

**次优方案（1 行，弱）**：把 `chunk_size = (nek1+nth-1)/nth` 改成按 `nth*4` 切块（照抄另一条路径的
`nth_scaled`），每线程块压到 700 KB → 预期 α 2.18 → ~1.7，约 +12%。只能把拐点推远，不能消除。

## 12.7 分离实验：路径 A/B 与「量化 V」是两个独立问题

写 spec 时补测的一组对照（0.6B Q2_K，ctx=8192，t=12，n=96）。
`BW_eff` 由 legacy f16 标定：23.6 × 1.213 = **28.6 GB/s**。

| 配置 | FA 路径 | tok/s | 名义字节/token | 反推 α |
|---|---|---|---|---|
| FA f16 / f16 | A（split_kv，`nek1>=512`） | 12.5 | 1.213 GB | **2.20** |
| FA **q8_0 / f16** | B（k.type != v.type ⇒ 不满足 split_kv） | **17.3** | 1.001 GB | **1.95** |
| FA **q8_0 / q8_0** | B（`kv_is_f32_or_f16` 为假） | **10.5** | 0.765 GB | **5.37** |
| legacy f16 / f16 | — | 23.6 | 1.213 GB | 1.00（基准定义） |
| legacy q8_0 / f16 | — | 22.8 | 1.001 GB | 1.06 |

以及 ctx=256（<512 ⇒ **强制走路径 B**，KV 仍是 f16）：

| 配置 | tok/s |
|---|---|
| FA f16 / f16（路径 B） | 76.0 |
| legacy f16 | 73.6 |

### 结论（推翻了之前两个假设）

**(1) 路径 A 与路径 B 的 α 都是 ≈2（= GQA 比），路径 B 没有额外的结构惩罚。**
ctx=256 强制走 B 时 FA 反而略快于 legacy（76.0 vs 73.6）。
→ 修复方案**必须同时覆盖两条路径**，否则 K 量化的配置（走 B）拿不到收益。
这也是 §12.5 的方案要补路径 B 的原因。

**(2) 「-fa auto 恒等于 -fa on 所以很慢」的完整链条现在清楚了：**
量化 KV 时 `kv_is_f32_or_f16` 为假 → 落 B；`-ctk q8_0 -ctv f16` 时 `k.type != v.type` → 也落 B。
**只有 KV 同为 f16/f32 且 ctx>=512 才走 A。**

**(3) 量化 K 是本次性价比最高的目标配置，量化 V 则是另一个缺陷。**
- K=q8_0 + V=f16：**17.3**，已经比 f16/f16 的 12.5 快 38%，且**今天就是合法配置**
- 但把 V 也量化：字节从 1.001 降到 0.765 GB，速度却从 17.3 掉到 **10.5（−39%）**
  → α 从 1.95 跳到 **5.37**，即**在 GQA 重读之外还有约 2.7× 的额外开销**

**(4) 因此 §11 的立论前提要改。**
§11 的动机是"legacy 不支持量化 V，所以必须让 FA 追平 legacy 才能用量化 V"。
实测表明：**量化 V 在 FA 下同样是负收益**（哪怕它是合法的）。
真正该要的是 **量化 K + V 保持 f16** —— 这条路今天就是合法的，
只差 FA 的 α 从 2 降到 1。**§11 描述的"那个 +35%"应当作废，
修正后的目标见 `specs/fa-gqa-loop-reorder.md`。**

### 待查（下一个靶点）

`-ctv q8_0` 的那 ~2.7× 额外开销来源未查。候选：
- `v_to_float` 对量化类型的反量化未走 SIMD
- 量化 V 的行跨距 136 B（128 元素 × 34/32）破坏 64 B 缓存行对齐
- `v->type != F16` 分支改用 f32 累加器 `VKQ32`（而非 f16 的 `VKQ16`），寄存器/L1 压力翻倍

**不得臆断，必须实测区分。**

## 13. Spec 02 实现结果：消除 GQA 重读（已实现，验收部分通过）

规格：`specs/fa-gqa-loop-reorder.md`。改动只落在 `ggml/src/ggml-cpu/ops.cpp`。
**这条记录同时是对 §12 的更正 —— 实测推翻了该节的部分结论。**

### 13.1 改了什么

- 新增 `ggml_compute_forward_flash_attn_ext_f16_gqa()`：循环序由
  `for 每个 q 头 { for 每个 token { 读 K/V } }` 改成
  `for 每个 kv 头组 { for 每个 token { 读一次 K/V；组内 q 头复用 } }`
- ic 循环体与收尾提取成 `ggml_fa_f16_step()` / `ggml_fa_f16_finalize()`，
  **原内核与新内核共用同一份算术**，结构上不可能漂移（满足 spec §6.5）
- 路径 A（split_kv）与路径 B（q 行分块）都接入；路径 B 改为按 kv 头组对齐切块
- 累加器放栈上（rk2≤8 / DV≤256 / Q 行≤1024 B），**不动 wdata 预算**
- `LLAMA_FA_GQA=0` 不重编译即可回滚
- 实测后新增两条回落条件：
  - **V 被量化时不分组**（首轮 −10%，见 13.4）
  - **`nek1 >= 4096`**：收益随 KV 占比增长，低于此点不划算。这条对本项目尤其重要 ——
    魔改 #1 的 `-fakv 2048` 会关掉长上下文的 FA，所以 **FA 默认只在短上下文生效**，
    而那一段正是分组会轻微变慢的区间，不设门槛就会让默认路径变慢

### 13.2 正确性：bit-exact 通过（一票否决项，全过）

改动前另编一份 `bin-base` 作对照，`--temp 0 -n 256` 逐 token 比对，**6/6 完全一致**：

| 模型 | 量化 | -fa | ctx | 结果 |
|---|---|---|---|---|
| Qwen3-0.6B | f16 | 1 | 512 | IDENTICAL |
| Qwen3-0.6B | f16 | 1 | 8192 | IDENTICAL |
| Qwen3-0.6B | Q2_K | 1 | 8192 | IDENTICAL |
| Qwen3-0.6B | Q2_K | 1 | 8192 + `-ctk q8_0 -ctv f16` | IDENTICAL |
| Qwen3-4B | q4_k_m | 1 | 8192 | IDENTICAL |
| Qwen3-0.6B | Q2_K | 0（legacy 未被波及） | 8192 | IDENTICAL |

### 13.3 性能实测

方法：为消除跨批次漂移，**同一二进制内 `LLAMA_FA_GQA=0`（回落）与默认（分组）交替各跑 2 次**。
平台 Qwen3-0.6B Q2_K，`-t 12`，`-n 128`。

| 配置 | 路径 | 关闭 | 开启 | 变化 | 同批 legacy |
|---|---|---|---|---|---|
| KV f16/f16 @8192 | A | 11.2~12.5 | **12.9~15.1** | **+14~22%（中位 +17%）** | 20.0 |
| `-ctk q8_0 -ctv f16` @8192 | B | 14.75 | **17.85** | **+21%** | 22.0 |
| KV f16 @4096 | A | 25.7~25.8 | 25.5~26.3 | 噪声内（±1%） | — |
| KV f16 @≤2048 | A/B | — | — | 门槛已关闭分组，差异落在噪声内 | — |

**两点测量纪律（都踩过坑）：**

1. **配对顺序会引入偏差**：所有配对原本都是"先 off 后 on"，若机器状态单调漂移，比值被高估。
   ctx=8192 做**反序**复测（先 on 后 off）仍得 +14.5% / +19.2% → 增益真实，不是顺序假象。
2. **ctx≤2048 的噪声是 ±5~8%**（同一命令 off 值跨度 42.1~45.8），
   这一区间任何小于 5% 的"差异"都不可信，因此用门槛关掉分组而不是去争噪声里的零点几。

### 13.4 `-ctv q8_0` 的处理

首轮实现后实测 **−10%**，根因找到：分组内核只把 V 的**加载**提到组外，
**反量化仍按 q 头各做一次**，且共用一个 V32 缓冲引入了写后读串行。
按 spec §1.1（量化 V 本就是独立缺陷、不在目标内）**加入回落条件**，改完由代码保证与改动前同路径。

⚠️ 该配置的绝对速度在本机**无法稳定测量**（同一命令同一二进制实测跨度 3.0~15.3 tok/s，
疑为笔记本功耗/温度墙导致），因此不对它下任何速度结论，只保留代码层面的保证。

### 13.6 对 §12 的更正：α 这个判据失效了（本篇最重要的一条）

§12 用"反推 α ≈ GQA 比"判定 GQA 重读是 FA 长上下文变慢的主因，据此预测修复能带来 ~+90%。
**实测只有 +14%。**

反推检验：修复后若 α 真降到 1，则 12.95 tok/s 对应
`12.95 × (0.317 + 0.896) = 15.7 GB/s`；而同批 legacy 达成 `20.0 × 1.213 = 24.3 GB/s`。
**FA 只拿到 legacy 65% 的带宽效率。**

两种可能解释（**未区分，不得择一采信**）：
1. 重复读本来就被 L2 吸收 —— 每线程每 kv 头组的工作集是 683 token × 512 B = 350 KB，进 L2，
   所以"去掉重复读"省下的本来就不多；**那么 α≈2 这个拟合值从来就不代表真实 DRAM 流量**
2. FA 的流式内核本身达不到 `mul_mat` 的 DRAM 效率（去掉重复读后仍差 35%）

两者都指向同一结论：**GQA 重读是真实因素，但只是 FA 长上下文惩罚的一小部分；
主因另有其处，且 α 作为判据已经失效。**
下一步要直接测量 DRAM 流量或做受控实验区分，不得再靠 α 拟合下结论。

| 项目 | spec 预测 | 实测 |

| FA q8_0/f16 @8192 | ~22 | 17.85 |

但它**没有兑现"让 FA 追平 legacy"**，所以 §11 那个 +35% 仍然拿不到。
当前长上下文最优仍是 **legacy + 量化 K**（22.0）+ 投机命中（§10.6 的 26~33）。

## 14. 选项重排：B 判死刑、A 降级、D 上位（2026-09-27）

### 14.1 今晨三组新数据

1. **PPL 恢复**（见 §11.6 勘误）：exit 139 根因是 09-25 的残次 `llama-perplexity-impl.dll`，
   `ninja llama-perplexity` 重编即好。**客观质量门回来了。**

   → 注意力并行度 ~12 封顶，8 线程瓶颈坐实
3. **配对批次**（平衡顺序 on/off/off/on + legacy×2，t=12）：

   （今晨绝对值比昨日下午整体高 ~15%，机器状态漂移；**只看批内比值**）

### 14.2 每线程带宽拆解（@8192，q8K/f16V，KV=0.672 GB/tok）

| 配置 | t/s | 注意力线程 | 每线程 GB/s |
|---|---|---|---|
| 分组 path B（FA） | 22.0 | **8**（=kv头组数，bit-exact 下限） | **1.85** |
| legacy | 25.5 | 12 | 1.43 |

- 分组内核**每线程带宽比 legacy 高 30%** —— path B 输的只是线程数
- **legacy 已在屋顶线**：25.5 × 0.989 GB/tok = 25.2 GB/s ≈ 有效带宽上限
  → 任何"让 FA 追平 legacy"的方案（含 B）天花板就是 legacy，**收益归零**
- "FA 65% 效率"拆解：path A（f16 V，12线程）每线程仅 0.97 —— 低效 specifically 在
  f16 V 累加路径（VKQ16 + 在线 rescale），不是 FA 的普遍属性

### 14.3 结论

- **B 出局**：上限=legacy=屋顶线；且默认配置（`-fakv 2048`）长上下文本就走 legacy
- **A 降级为学术题**：其价值前提"FA 修好才能解锁量化 V"被 D 消解
- **D 上位（唯一能破屋顶线的路线）**：legacy 图 + 量化 V 自定义算子

### 14.4 方案 D 概要（待 spec）

- 保留 legacy 的 K 侧 mul_mat 与向量化 softmax；只把 V 侧 mul_mat 换成自定义算子：
  `out[qh][d] = Σ_t kq[qh][t] · dequant(V[h][t][d])`
  —— 无 expf、无在线 max、纯加权行和 + FMA，算力开销可忽略，纯带宽题
- 前提：解耦 `v_trans` 与 `flash_attn`（量化 V 时强制 FA 布局 `[d][h][t]`，dim 连续 →
  块寻址合法；两处布局已核实 `llama-kv-cache.cpp:1299`）
- **已证伪的捷径**：legacy 图用现有 op 消化 FA 布局 V = `cont(transpose(v))` 物化整块转置，
  即 §12 记录的 ctx8192 每 token +940 MiB 灾难 → 必须自定义算子，没有免费午餐
- 线程：按 (head, token 段) 切 + partials 归约 → 12 线程满并行；**天然不 bit-exact**
  （V 本身量化了，无逐位基线可言），验收改用 PPL 门 + f16-V 时与 legacy 生成对照
- 预期：q8K/q8V = 0.765 GB/tok ÷ 25.2 GB/s ≈ **33 t/s**（vs 今日 25.5，+29%）；
  与投机命中叠加：26~33 → 32~42

### 14.5 bit-exact 取舍的最终答案

PPL 门恢复后，"放弃 bit-exact"从"放弃客观验证"降级为"换验证仪器"（diff → PPL）。
后续内核改动的默认验收标准改为：**f16 等价配置生成对照 + 量化配置 PPL 增量 ≤ 容差**。

## 15. Spec 03 实现结果：算子正确，但不划算（默认关闭）

规格：`specs/legacy-quant-v-op.md`。**本篇同时是对 §11 和 §14 的更正 —— §14 把 D 捧为"唯一能破屋顶线的路线"，实测不成立。**

### 15.1 真正的 bug：v_trans 的决定点漏了 10 处

初版只在 `llama-model.cpp` 的 3 处 hybrid 分支（带 `/* attn_v_trans */` 注释的）替换了
`!cparams.flash_attn`，而 Qwen3-0.6B 实际走的是第 2820 行 `new llama_kv_cache(...)` ——
那里仍是上游原值。结果 `attn_v_trans = true` → V 存成转置布局 → 图里走 `else` 分支
`mul_mat(v, kq)`，**TQ 算子根本没被派发**，看到的"垃圾输出"就是量化 V 被 mul_mat 按错误
粒度读取的结果（§11.3 同一现象）。

修法：把 `attn_v_trans` 提到 `create_memory()` 函数开头统一计算，`params.type_v,` 之后的
13 处 v_trans 实参全部指向它。**单一真源，否则图与 cache 布局会各说各话。**

派发确认（`LLAMA_TQ_DEBUG=1`）：`v_trans=0 v_type=q8_0 v_ne=[128,2048,8,1] use_tq=1`。

### 15.2 顺手测出来的"诱惑"：转置布局 + 量化 V 能跑 32.8 t/s，但输出是垃圾

`LLAMA_QV_LEGACY_LAYOUT=1` 保留上游转置布局、同时解除硬禁，让量化 V 直接喂给 `mul_mat`：

| 配置 | ctx 8192, t=12 | tok/s | 输出 |
|---|---|---|---|
| 转置布局 + q8K/q8V + mul_mat | 825 MB/token | **32.8 / 31.7** | **垃圾**（`以下 searchData…`） |
| legacy + q8K/f16V（今日最优） | 1033 MB/token | 25.5 | 正常 |

32.8 t/s 正好是 §14.4 预测的屋顶线（0.765 GB ÷ 25.2 GB/s ≈ 33）——**这条路快得诱人，但它是错的**。
§11 的结论由此**重新成立**：上游那条禁令有道理，我在 §14 里推翻它推错了。

### 15.3 算子自身的代价：不是量化的问题，是结构问题

让 **f16 的 V** 也走 TQ（`LLAMA_QV_FORCE=1`），此时没有任何反量化，TQ 与上游 `mul_mat`
搬同样的字节、算同样的值，唯一差别是内核结构：

| V 类型 | 字节/token | TQ 内核 | 上游 mul_mat | TQ/上游 |
|---|---|---|---|---|
| f16 | 1242 MB | 13.3 | 23.3 | **0.57** |
| f16（配 q8 K） | 1033 MB | 13.3 | 25.1 | **0.53** |
| q8_0 | 825 MB | 17.2 | —（不可运行） | — |

**即使完全不反量化，TQ 也只有 mul_mat 约 55% 的带宽。** 根因是两种求和形态的差别：

- `mul_mat`：每个输出元素做**一次长度 T 的连续点积**（两条连续流、SIMD 全流水）
- TQ：每个 token 做**一次长度 D=128 的 axpy**，每搬 136 字节就要付一整套循环/调用开销

把模式一从"(token 块, kv 头) 切分"改成"连续 token 块、kv 头在内层"（消除 1088 字节跳跃
和 cache line 被 2~3 个头组重复拉取）只换来 **16.3 → 17.2（+5%）**，说明带宽不是主要约束。

### 15.4 判决：G3 不通过，默认关闭

| 场景 | TQ q8K/q8V | 今日最优（legacy q8K/f16V） | 判定 |
|---|---|---|---|
| decode @8192 | **17.2** | **25.5** | **0.67×**（门槛 1.10×） |
| prefill @8192 | **114** | **127** | **0.90×** |

两个场景都输，连"反量化可被 batch 摊薄"的 prefill 都输 11%。
按 spec 自己的门槛 G3，**本改动不启用**：`LLAMA_QV_OP` 默认关闭，恢复上游语义
（量化 V + `-fa 0` 报 `quantized V cache requires flash_attn`），`LLAMA_QV_OP=1` 打开。

### 15.5 正确性：算子是对的（保留代码，不保留默认）

- **默认路径 bit-exact**：**6/6** 用例与改动前二进制逐位一致（legacy f16 @8192、FA f16 @512、
  legacy q8K/f16V @8192、f16 模型 FA @512、FA f16 @8192、legacy f16 @512）
- **生成文本对照（G6，f16 模型，temp=0）**：legacy+TQ(q8V) vs FA(q8V) —— 两条完全独立的
  实现对同一数学对象，**前 51 个词逐词一致**（221/173 token，29%）后才因求和顺序分岔：
  > TQ: `Okay, let's see. The user provided a series of sentences that seem to be repeating the
  > same message. The original sentence is: "The quick brown fox …"`
  > FA: `… seem to be repeating the same message. The original text is: "The quick brown fox …"`
  三路（TQ q8V / FA q8V / legacy f16V）都是通顺英文，无一例垃圾。
- **f16 V 走 TQ vs 上游 mul_mat**：PPL 21.9676 / 21.9692 vs 基线 21.9684 → 偏差 0.0036%
  （作为标尺：legacy 与 FA 互比本身就差 0.0014%）
- **模式一致性**：固定 batch 只切模式，模式一在 `n_chunk=1` 时**逐位等于**模式二
  → 索引/步长无错，残余差异纯为 partials 求和顺序
- 差异被量化 KV 放大：f16 KV 下模式间差 0.007%，q8_0 KV 下 0.06~0.19%（softmax 变尖后
  浮点末位就能翻转主导 token）

### 15.6 方法教训（两条，都踩过）

1. **Q2_K 模型是坏转换，不能当质量判据**：f16 模型 PPL 21.97，Q2_K 模型 264~321，
   且连"量化 K 反而降 PPL"这种不可能的排序都出现。所有质量对照改用
   `models/Qwen3-0.6B-f16.gguf`；速度测量不受影响（字节数不变）。
   **连文本级对照都不能用它**：它连纯上游路径（legacy + f16 V）都吐 `:- ** 妻 **`，
   所以"几分之几的词一致"这种指标在它上面恒等于 0，会伪装成算子 bug（§15.1 的 0/251 里
   就掺了这个噪声）。`verify_spec03.sh` 的 G5/G6 段已强制改用 f16 模型。
2. **纯上游配置都满足 batch 无关性**（legacy f16/f16 在 -b512 与 -b8 都是 21.9684），
   所以"同一配置换 batch 后 PPL 变了"是一个灵敏的 bug 探测器 —— 第一次就是这样发现
   两个模式不一致的。

### 15.7 对路线图的影响

- §14.4 的"D 是唯一能破屋顶线的路线"**作废**：屋顶线 32 t/s 属于一条会输出垃圾的路径；
  能正确算出结果的两条路（FA 12.7、TQ 17.2）都到不了。
- **量化 V 在 CPU decode 上就是负收益**，与 §12.7 的 α=5.37 现象同源：反量化按字节计的代价
  高于省下的带宽，而 decode 时复用倍数只有 `rk2 × N = 2`，摊不开。
- 长上下文最优仍是 **legacy + 量化 K + f16 V（25.5）**，叠投机命中（§10.6）到 26~33。
- 剩下的"减字节"空间只剩 K 侧（已做）和权重（已做），**长上下文这条路基本走到头了**。

## 16. 常驻化：TTFT 63.5s → 0.24s（llama-server 实测）

动机：§15 之后我们发现**一直在优化只占端到端 9% 的 decode**。本节回答"另一边的大头能怎么消掉"。

### 16.1 为什么必须用 llama-server 测

| 工具 | 问题 |
|---|---|
| `llama-bench` | tg 指标**不带 prompt 上下文**（JSON 里 tg 那行是 `"n_prompt": 0`），测不出上下文效应 |
| `llama-cli -f` | 每次新进程，全量重算，测不出"跨轮复用" |
| `llama-server` | slot 保留 KV；日志 `prompt eval time = X ms / N tokens` 的 N = `n_prompt_processed`，即**实际重算**的 token 数（缓存命中的不计入） |

脚本：`ctest/ttft_server.sh`（两轮最小对照）、`ctest/ttft_server2.sh`（真实一轮的拆分）。

### 16.2 结果（f16 模型 / t=12 / -fa 0 / q8K + f16V / ctx 6734）

| | prompt 重算 | TTFT | 生成 | 端到端 |
|---|---|---|---|---|
| turn 1（冷） | **6734 tok**（全量） | **65,766 ms** | 8 tok @ 13.9 t/s | 66.3 s |
| turn 2（热，+22 tok） | **22 tok** | **391 ms** | 200 tok @ 13.9 t/s | **14.7 s** |

- **TTFT 降 168×**（65.8 s → 0.39 s）。增量 prefill 只算新增 token，与上下文长度无关。
- 增量 prefill 的**每 token 成本反而更高**：17.8 ms/tok vs 全量的 9.77 ms/tok（小 batch 效率低），
  但绝对量小到无所谓。
- 长上下文 decode 稳定在 **13.9 t/s**（f16 权重 @6734）。

### 16.3 真实一轮的拆分：TTFT 只占 2.7%

常驻之后，用户等待 14.7 s 里的构成：

| 部分 | 时间 | 占比 |
|---|---|---|
| 增量 prefill（TTFT） | 0.39 s | **2.7%** |
| 生成 200 token | 14.3 s | **97.3%** |

⇒ **常驻化把 prefill 问题解决掉了，剩下的全是 decode。**
⇒ 想再压缩用户等待，只能动 decode —— 而 decode 撞的是带宽/反量化墙，主时间轴上已经挤不出来。

### 16.4 对"空闲时段计算"的意义

- 20 s 空闲窗口 × 13.9 t/s = **278 token**，大于一轮典型回复（200）。
  ⇒ **预生成一整轮的时间预算是够的，约束不在时间，只在命中率。**
- ~~用户等待公式：`TTFT + (N − k)/13.9`，k = 预生成命中长度。~~
  ~~k=0 → 14.8 s；k=100 → 7.6 s（1.94×）；k=200 → 0.39 s（38×）。~~
  ~~收益 = `1/(1 − k/N)`，线性。~~

  **⚠ 上面三行作废（2026-09-28 更正，见 §17.2）**：预生成的是**助手的回复**，不是
  用户输入的前缀，所以收益是**二元的**（猜中意图→整轮白送），不能按 token 线性折算。
  正确模型：
  ```
  命中   (概率 p)  : 等待 ≈ prefill(用户输入) ≈ 0.36 s
  未命中 (概率 1-p): 等待 = TTFT + N/r = 14.78 s
  speedup = T_miss / (p·T_hit + (1-p)·T_miss) ≈ 1/(1-p)
  ```
  上面"20 s 空闲窗口够预生成一整轮"这条仍然成立（时间预算不是约束），
  但"k 由可预测性决定"的线性表述是错的，一律以 §17 为准。

### 16.5 权重类型 vs 上下文（无上下文 tg128，t=12，-fa 0）

| 权重 | 大小 | t/s | 等效带宽 = 大小×t/s | 相对 f16 |
|---|---|---|---|---|
| f16 | 1509 MB | 33.9 | 51.1 GB/s | 100% |
| q8_0 | 799 MB | 55.3 | 44.2 GB/s | 86% |
| q4_k_m | 484 MB | 61.3 | 29.7 GB/s | **58%** |
| q2_k | 347 MB | 78.2 | 27.1 GB/s | **53%** |

若真被内存带宽卡死，q2_k（字节为 f16 的 1/4.35）应跑 147 t/s，实测 78.2。
⇒ **§14 以来记的"有效带宽 25~31 GB/s"作废**——那是拿 Q2_K 测出来的**反量化吞吐**，不是机器带宽。
⇒ 卡住我们的不是带宽，是**量化越狠、反量化越贵**的收益递减。
⇒ 新靶点：**q4_k_m 只有 58% 效率，修到 85% 就是 61 → 90 t/s**（比三天来的内核魔改都大）。

### 16.6 顺带修正

- `ctx_8192.txt` 实际是 **6734 token**（不是 8192），所以 §15 引用的"8192 prefill 79 s"
  按本文件算应为 **63.5~65.8 s**；`llama-bench -p 8192` 的 103.4 t/s 是真实 8192 的速率，两者不矛盾。

  **待办**：同一长上下文下把 f16 / q8_0 / q4_k_m / q2_k 四种权重拉一遍，确认长上下文的最优权重类型。

## 17. 命中率探针：空闲时段预生成的天花板只有 1.2~1.3×（判决：不做）

### 17.1 为什么必须测这个

§16.3 实测：常驻化之后一轮 14.7 s 里 TTFT 只占 2.7%，剩下 97.3% 全是 decode。
decode 撞的是带宽/反量化墙，主时间轴上挤不出来。**空闲时段是唯一不在主时间轴上的
算力**，但它能兑现多少，完全取决于命中率 p —— 而这个数在此之前是零。

本节用真实人类多轮语料把 p 的天花板测出来。脚本：`ctest/probe_hit.py`。

### 17.2 判定模型（更正 §16.4）

预生成的是**助手的回复**，不是用户输入的前缀，所以收益是**二元的**：

```
命中   (概率 p)  : 回复已在手上，用户等待 ≈ prefill(用户输入)        ≈ 0.36 s
未命中 (概率 1-p): 回到原路径，用户等待 = TTFT + N/r                = 14.78 s

E[等待] = p·T_hit + (1-p)·T_miss
speedup = T_miss / E[等待] ≈ 1/(1-p)
```

§16.4 原先写的"按 token 线性折算 k"是错的，已在原处标注作废。
（时间预算那条仍然成立：20 s 空闲 × 13.9 t/s = 278 token > 一轮 200 token，
**约束不在时间，只在命中率** —— 这句没变。）

### 17.3 数据源与方法硬约束

| 约束 | 做法 |
|---|---|
| 必须真实人类对话 | OASST1 `ready` 子集，`synthetic` 字段 88838/88838 全为 False（已核对） |
| 不许自己命中自己 | 候选只从 **train split** 构造，在 **test split** 上测 |
| 不许跨线程泄漏 | 按 **对话树**切分（不是按消息），3 折不同随机种子 |
| 不许自证 | 自检项：oracle 必须 100%、空候选必须 0%（两次运行均通过） |

**已排除的污染源**：UltraChat 被否掉了，它是 LLM 合成的对话 —— 用 AI 生成的数据
测 AI 的可预测性是循环论证。ShareGPT（真人对 ChatGPT，最贴合）因 921 MB / 1 GB
下载不可行而放弃，改用 OASST1。

**不可消除的 caveat（必须带着读）**：OASST1 的 assistant 回复也是**人类**写的，
而我们场景里 assistant 是 LLM。本探针测的是"真人对人类回复的反应"，作为
"真人对 LLM 回复的反应"的代理，**偏差方向未知**。

### 17.4 判据，以及对判据本身的校准

| 判据 | 含义 | 问题 |
|---|---|---|
| LCP | token 级最长公共前缀 | 过严：用户说 "Can you expand on that?" 和候选 "Tell me more..." 同一意图，LCP 却是 0 |
| COS | char-4gram TF-IDF 余弦 | 过松且区分度有限 |

**先校准判据再信它**。18 对人工构造的同义句 vs 18 对错位异义句：

```
同义句对 cos: 均值 0.144  中位 0.136  min 0.000  max 0.486
异义句对 cos: 均值 0.022  中位 0.000  max 0.345
AUC = 0.793
```

**AUC 0.793 < 0.9 ⇒ 语义判据区分度不足，P(cos) 列只能当参考，不能当结论。**
（LCP 列不受影响，它是纯字面比较。）

### 17.5 结果

**字面可预测性（3 折均值）**

| 语料 | 边界 | 策略 | P(≥1) | P(≥2) | **P(≥4)** | P(≥8) |
|---|---|---|---|---|---|---|
| en 全量 | 2295 | S1 上下文检索 K=32 | 52.0% | 25.7% | **1.4%** | 0.0% |
| en 全量 | 2295 | Srand 随机候选 K=32 | 49.6% | 23.0% | **1.4%** | 0.0% |
| en 全量 | 2295 | S0 高频前缀 K=32 | 40.8% | 20.4% | **1.5%** | 0.0% |
| en 创作型 | 368 | S1 上下文检索 K=32 | 43.3% | 23.1% | **0.3%** | 0.0% |
| en 创作型 | 368 | Srand 随机候选 K=32 | **45.9%** | 22.0% | **0.3%** | 0.0% |
| zh | 233 | S1 上下文检索 K=32 | 31.3% | 2.6% | **0.4%** | 0.0% |

两个致命观察：

1. **到第 4 个 token 就崩了**：所有策略、所有语料的 P(≥4) 都在 0.3~1.5%。
   （`S0b 首token K=32` 的 P(≥1) 能到 70%，但那只是猜中 "Can"/"The"/"What"
   这类常见首词，不是意图命中，P(≥2) 立刻归零。）
2. **上下文检索几乎等于随机挑**：全量上 S1 52.0% vs 随机 49.6%（微弱信号）；
   **创作型上 S1 43.3% 反而低于随机 45.9%**。即"相似上下文 ⇒ 相似用户下一句"
   这个假设基本不成立 —— 这正是检索式预生成赖以成立的前提。

**意图分布：与预测器无关的天花板**

把用户下一句按"能不能提前把回复生成好"分类（pre=可预生成 / weak=依赖上下文或
收益小 / no=全新任务）：

| 意图 | en 全量 | en 创作型 |
|---|---|---|
| other | 36.1% | 32.9% |
| newtopic（全新话题） | 28.1% | 19.6% |
| thanks/end | 11.0% | 13.6% |
| elaborate | 6.3% | 6.8% |
| why | 4.6% | 1.6% |
| code | 4.3% | 9.0% |
| example | 3.1% | 1.9% |
| rephrase | 2.4% | 4.3% |
| **continue** | **2.1%** | **6.2%** |
| fix | 1.4% | 3.3% |
| translate | 0.6% | 0.8% |
| **可预生成(pre) 合计** | **15.9%** | **23.4%** |
| 不可能(no) 合计 | 64.2% | 52.4% |

这一点是本节最有价值的结论：**天花板不是由预测器质量决定的，是由"用户下一句有多少
比例属于可预生成意图"决定的**。即使预测器完美，64%（全量）/ 52%（创作型）的全新
话题谁也猜不到。所以换更强的预测器（包括用 LLM 生成候选）也突破不了这个数。

### 17.6 判决：不做

| 场景 | 可预生成(pre) | 加速上界 | 含 weak 的乐观上界 |
|---|---|---|---|
| 任务型对话（en 全量） | 15.9% | **1.18×** | 1.54× |
| 创作型对话（en 子集） | 23.4% | **1.30×** | 1.87× |

上界性质：假设意图识别完美 + 每个分支只需一条预生成回复 + 预生成内容用户真会要。
**真实值只会更低**（探针里所有实际策略的 P(≥4) 都只有 0.3~1.5%，远低于意图上界）。

对照目标：我们要的是把 14.7 s 压下去、把长上下文推到 100 tok/s 量级。
**1.18~1.30× 做不到这件事**，而代价是 CPU 常满载（功耗、发热、风扇噪音）+ 用户
回来时的抢占延迟 + 一整套命中判定的工程量。

⇒ **空闲时段预生成这条路线到此为止，不再投入。**

### 17.7 遗留与已知缺陷

- **中文意图分类无效**：规则是英文正则，zh 语料 99.1% 落进 `other`，该列已作废
  并在脚本里加了硬警告。zh 只有 LCP/cos 列可用（且样本仅 233）。
- **PREDICTABLE 分类是主观判断**。敏感性：把 weak 计入后上界升到 1.54×/1.87×，
  这是乐观区间，不是预测。
- **没测 LLM 生成候选**（S3）。但按 17.5 的论证，预测器质量不改变意图天花板，
  所以不会翻转结论；若真要测，用 llama-server 在每个边界采样 K 条候选即可。
- **数据源场景错配未解决**：OASST1 是众包任务型对话。创作型子集是我能拿到的最接近
  代理（pre 从 15.9% 升到 23.4%，说明场景确实敏感），但仍不是真实的"人↔LLM 创作
  多轮"日志。要彻底回答需要真人对话日志。

## 18. 「实际使用效率」的可测量定义：常驻化的另一半是跨进程持久化

### 18.1 为什么本节存在

用户主张：**目标不是 tok/s，是实际使用效率。** 这个主张成立，但"效率"是模糊词，
不落成可判定条款就还是漂亮话。本节做两件事：

1. 把"实际使用效率"拆成三个**可测量维度**，每个配一个**外部刻度**；
2. 测出 §16 那个 168× 的**隐藏前提**——它只在进程活着时成立。

刻度来源：Jakob Nielsen 的三个响应时限（0.1s / 1s / 10s，NN/g，基于 Miller 1968、
Card et al. 1991，四十多年未变）：

- **0.1 s** —— 用户感觉是自己在直接操作，不需要任何反馈提示
- **1.0 s** —— 思路流畅不被打断；用户注意到延迟，但仍感觉在控制中
- **10 s** —— 注意力的极限；**超过它用户开始想别的事，等回来时脑子难以回到轨道**

### 18.2 三个维度（tok/s 一个都不在里头）

| 维度 | 定义 | 刻度 | 冷启动 | 常驻（同进程） | 跨进程（restore） |
|---|---|---|---|---|---|
| **恢复成本** | 中断后到第一个可用输出 | < 10 s 保住注意力 | **66.4 s** ✗ | 0.39 s ✓ | **3.5 s** ✓ |
| **首反馈延迟** | 流式首 token 到达 | < 1 s 思路不断 | **63.5 s** ✗ | 0.39 s ✓ | **0.09~0.22 s** ✓ |
| **阅读跟随性** | 生成速度 vs 人类阅读 | > 阅读速度 → 永远在读不在等 | 13.8 ✓ | 13.8 ✓ | 13.8 ✓ |

人类阅读速度参照：200~250 wpm ≈ **4.3~5.5 tok/s**（按 1 词 ≈ 1.3 token 折算）。
本机长上下文生成 **13.8 tok/s ≈ 阅读速度的 2.5~3.2 倍**。

⇒ **单用户交互场景下，用户是被自己的阅读速度限制的，不是被模型限制的。**

### 18.3 实测：跨进程持久化（llama-server 现成能力，零改动）

`--slot-save-path` + `POST /slots/{id}?action=save|restore`。官方测试
`tools/server/tests/unit/test_slot_save.py::test_slot_save_restore_with_image_across_restart`
已证明跨进程恢复可用，本节测的是**它在本机长上下文下要花多少**。

脚本 `ctest/ttft_persist.sh`、`ctest/ttft_stream.sh`。f16 模型 / t=12 / -fa 0 /
q8K+f16V / ctx 6734：

| 步骤 | 实测 |
|---|---|
| turn 1 冷启动 prefill | `prompt_n=6734  prompt_ms=63411`（63.4 s） |
| **save** | **465 ms**，`n_saved=6749`，`n_written=592,724,892 B`（**565.3 MiB**） |
| — 杀掉进程（模拟崩溃/重启）— | |
| 新进程启动（model load） | 3 s |
| **restore** | **310 ms**，`n_restored=6749`（565.3 MiB） |
| turn 2 增量 prefill | `cache_n=6749  prompt_n=10  prompt_ms=223` |

**prefill 部分：63,411 ms → 223 ms = 284×。**
**端到端含 model load：66.4 s → 3.5 s = 19×**（两者都摊 3 s 加载）。

save 465 ms / restore 310 ms 对应 ~1.2 GB/s 写、~1.8 GB/s 读 —— 都在空闲时段
完全付得起，且**远小于它省下的 63 秒**。

### 18.4 成本常数：85.4 KB / token

`565.3 MiB / 6749 token = 85.4 KB/token`（q8_0 K + f16 V）。这是两个方向的定价：

- **持久化（③）**：6734 token 一轮 = 565 MB/轮。多轮全存会线性膨胀，
  需要淘汰策略（只存最近 N 轮，或只存"根部"长上下文 + 增量）。
- **分支保留（②）**：每条分支 565 MB。3 个分支 1.7 GB —— 内存上可行，
  但**不是免费的**，别当成零成本设计。

### 18.5 流式：首 token 才是用户感知的延迟

`stream=true` 实测（restore 后的热 slot）：

```
stream short (16 tok)       first_chunk= 216.3 ms   total=  1.30 s   13.03 tok/s
stream full reply (200 tok) first_chunk=  86.1 ms   total= 14.55 s   13.82 tok/s
```

注意对比：**总时长 14.55 s 超过 Nielsen 的 10 s 注意力阈值，但用户 86 ms 就开始读了。**

这就是流式的意义——它把"感知延迟"从总时长解耦成首 token 时间。14.55 s 的那一行
不该读成"用户等了 14.55 秒"，而该读成"用户读了 14.55 秒，且内容一直比他读得快"。

（200 tok 那次首 chunk 更快，是因为前一次请求把剩余 10 个 token 也预热了，
slot 完全命中。）

### 18.6 结论：100 tok/s 是**分场景**的目标，不是全局目标

| 场景 | 什么决定体验 | 13.8 tok/s 够吗 |
|---|---|---|
| 单用户交互（对话、改稿、边写边改） | 首反馈延迟 + 恢复成本 + 阅读跟随性 | **够**：86 ms 首 token，生成快过阅读 2.5~3.2× |
| 批量生成（一次出整章 3000 字 ≈ 4000 tok） | 纯吞吐 | **不够**：4000/13.8 = 290 s ≈ 4.8 分钟；100 tok/s 才是 40 s |
| 多用户/多会话并发 | 聚合吞吐 | 不够 |

⇒ 如果用户的使用形态是**交互式创作**，那 100 tok/s 是过度目标，真正该做的是
本节这三件事（常驻 / 持久化 / 流式），它们**全是零改动或近零改动**。
⇒ 如果是**批量出稿**，那才需要回主时间轴硬挖（q4_k_m 58% 反量化效率那个靶子）。

**这一点必须先问清楚再投入：它决定后面所有优化的方向。**

### 18.7 遗留

- restore **不是自动的**：应用必须主动调 `action=save` / `action=restore`。
  llama-server 只提供能力，不做策略。这是"工程量"而非"算法难度"。
- 没测 KV 压缩后持久化（量化 K 已用 q8_0；若改 q4 K 则 565 MB → ~390 MB，
  save/restore 时间按比例下降，但会掉质量）。
- 85.4 KB/token 是 **Qwen3-0.6B / 28 层 / 8 kv head** 的数字，换模型要重算。
- 阅读速度 200~250 wpm 是英文成人平均；中文按 300~500 字/分钟折算需要另测，
  但结论方向不变（13.8 tok/s 仍在 2× 以上）。

## 19. 一个几十行的改动为什么会烧掉几万 token（实测分解）

### 19.1 问题

用户提问：AI 生成速度本该比人类快，为什么改一个几十行的文件要花几万 token？
**token 到底花在哪里？**

这不是速度问题，是**成本结构**问题。本节只用实测数字回答。

### 19.2 实测锚点：文件有多"贵"

用 Qwen3 tokenizer 实测（`transformers.AutoTokenizer`，与 GPT 系 tokenizer 同族，
绝对数不同但量级一致）：

| 文件 | 行数 | 字符 | **token** |
|---|---|---|---|
| `llama.cpp/ggml/src/ggml-cpu/ops.cpp` | 12,768 | 445,611 | **138,774** |
| `llama.cpp/ggml/src/ggml-cpu/ggml-cpu.c` | 3,987 | 134,808 | **37,016** |
| `ctest/benchmark_results.md`（本项目文档） | 1,448 | 46,621 | **29,737** |
| `ctest/probe_hit.py` | 639 | 21,948 | **7,599** |
| `specs/legacy-quant-v-op.md` | 282 | 11,476 | **6,801** |
| `ctest/ttft_persist.sh` | 124 | 4,492 | **1,537** |

**第一个结论：`ops.cpp` 一个文件就是 138,774 token —— 完整读一遍就超过 131 k 的
上下文窗口上限。** 所以 agent 实际永不"完整读一个大文件"，它靠 grep + 片段读 +
多次往返来逼近，而**这些往返本身又是 token**。

### 19.3 分解：几万 token 的五个去处

| # | 去处 | 性质 | 能省吗 |
|---|---|---|---|
| 1 | **系统提示 + 工具 schema** | 每轮固定重付 | 平台侧，用户不可控 |
| 2 | **探索**：grep / ls / 读文件片段 | 一次性的，但结果永久留在上下文 | 可裁剪 |
| 3 | **失败与重试**：编辑报错、测试失败、再改 | 纯损耗，但同样永久留上下文 | 可裁剪 |
| 4 | **工具输出**：bash 输出、diff、日志 | 常常比需要的长 10 倍 | 可裁剪 |
| 5 | **每轮重发整个上下文** | **这是乘数，不是加数** | 靠 KV 复用 / prompt cache |

第 5 条是主因。前四条决定了上下文长度 L，第五条把它乘以轮数 T。

### 19.4 根因：成本是 O(轮数 × 上下文)，不是 O(代码行数)

模型**不缓存"认识"**。每轮 API 调用都要把整个对话历史重新 prefill 一遍
（服务端 prompt cache 能打折，但逻辑上这份"读"仍发生，且任何前缀改动都会让它失效）。

累计输入 token = Σ(每轮上下文长度)。上下文线性增长时的量级：

| 轮数 | 初始 ctx | 最终 ctx | **累计输入** | 输入:输出 |
|---|---|---|---|---|
| 8 | 20 k | 40 k | **240,000** | **96 : 1** |
| 15 | 20 k | 60 k | **600,000** | **240 : 1** |
| 25 | 20 k | 90 k | **1,375,000** | **550 : 1** |

（输出固定按 2,500 token ≈ 200 行代码算）

⇒ **改 200 行代码烧掉 24~137 万输入 token 是正常的。输入:输出在 100:1 量级。**

### 19.5 本质：AI 输在"读"，不输在"写"

| | 生成（写） | 理解（读） |
|---|---|---|
| 人类 | 打字 ~1~3 token/s（瓶颈） | **≈ 0**：靠长期记忆和索引，不用重读项目 |
| AI | 13.8 tok/s（本机实测）→ 快 5~10 倍 ✓ | **每轮全价重读整个上下文** ✗ |

**人类写代码时"已经认识"这个项目；AI 每一轮醒来都是失忆的，要重新认识一遍世界。**
所以"AI 生成比人快"这个直觉在**写**这一侧成立，在**读**这一侧完全不成立——
而读才是 99% 的成本。

### 19.6 这跟本项目前 18 节是同一个问题

服务端那份"每轮重读"的成本，在本地就是**我们测过的 prefill**：

| | 每轮 prefill | 说明 |
|---|---|---|
| 冷启动 / 无复用 | **63,411 ms**（6,734 token） | §18.3 实测，这就是"每轮全价重读" |
| KV 复用后 | **223 ms**（只算新增 10 token） | `cache_n=6749`，**284×** |

⇒ **§16/§18 做的 KV 复用，就是本地版的 prompt caching。** 服务端按折扣价卖给你，
本地直接把它做成了 284×。

而且本地还有服务端没有的东西：**§18 的跨进程持久化**（save 465 ms / restore 310 ms），
让"认识"这件事**跨重启保留**——等价于给模型一份不会丢的长期记忆。

### 19.7 对目标的含义（回到 §18.6 的分叉）

- **按 API 计费**：成本 = 轮数 × 上下文。省法只有两个：**压缩上下文**、**减少轮数**。
  跟 tok/s 无关。
- **本地部署**：边际成本为零，但 prefill 时间仍是每轮的真实成本
  （6,734 token = 63.4 s；若无 KV 复用，一个 30 k 上下文的 agent 会话每轮就要 ~280 s）。
  ⇒ **本地部署做 coding agent，KV 复用不是优化，是能不能用的前提。**

### 19.8 待验证

- 19.4 的表格是**公式推演**，不是实测。要实测需要抓一次真实 agent 会话的每轮
  `prompt_tokens`（OpenAI/Anthropic 的 usage 字段每轮都返回），再求和。这个数据
  任何一次 Claude Code / Cursor 会话都能拿到，做一个就够。
- 没有本地 coding agent 的实测：本项目的交互形态是"人直接指挥"，不是 agent 自主循环，
  所以§19 的结构分解**尚未在本机用 agent 复现过**。
- 138,774 token 是 Qwen3 tokenizer 的数；GPT/Claude tokenizer 对代码压缩率不同，
  量级可信，绝对值要换 tokenizer 重算。

## 20. 「每轮重读」的困境：已解决 98%，剩下的是布局问题不是算力问题

### 20.1 问题

用户提问：每轮重读在 API 只是费用，在本地是**难以想象的算力压力**。能不能改变？

§19 论证了这个成本是 O(轮数 × 上下文)。本节实测它在本地的真实形态。
脚本 `ctest/kv_reuse_turns.sh`。

### 20.2 实测 A：只追加的 10 轮对话（ctx 439 → 592）

| 轮 | cache_n | prompt_n | prompt_ms | 复用率 |
|---|---|---|---|---|
| 1（冷） | 0 | 439 | **2409** | 0.0% |
| 2 | 446 | 10 | **76** | 97.8% |
| 3 | 463 | 10 | 81 | 97.9% |
| 4 | 480 | 10 | 76 | 98.0% |
| 5 | 497 | 10 | 79 | 98.1% |
| 6 | 514 | 10 | 89 | 98.2% |
| 7 | 531 | 10 | 95 | 98.2% |
| 8 | 548 | 10 | 87 | 98.3% |
| 9 | 565 | 10 | 83 | 98.3% |
| 10 | 582 | 11 | 81 | 98.1% |

**`prompt_ms` 在第 2~10 轮完全平坦（76~95 ms），不随上下文变长而增长。**
每轮只算新增的 10 个 token，复用率稳定 98%。

⇒ **在"只追加"模式下，"每轮重读整个上下文"这件事根本不存在。**
⇒ 成本模型从 **O(上下文 × 轮数)** 变成 **O(新增 token)**。

### 20.3 实测 B：只改前缀里的一句话

把系统提示的第一个词改掉（`careful` → `VERY careful`），其余一字不动：

```
cache_n=3  prompt_n=437  prompt_ms=2218  reuse=0.7%
```

**81 ms → 2218 ms，27×。439 个 token 里只有 3 个还能用。**

一个词的改动让整段缓存归零。这就是 KV 复用的硬约束：**必须逐 token 前缀相同**，
第一个不匹配的 token 之后全部作废。

### 20.4 结论：困境的性质被误判了

| | 原以为 | 实测 |
|---|---|---|
| 本地每轮成本 | O(上下文 × 轮数)，30 k ctx 每轮 ~280 s | **O(新增 token)**，稳态 ~80 ms |
| 瓶颈 | CPU 算力不够 | **有没有改前缀** |
| 解法 | 更快的 prefill / 更快的 CPU | **约束 prompt 布局与工作流** |

⇒ **这不是算力问题，是数据结构问题。** KV cache 是一个只能追加、不能随机写的
前缀树；一旦中间被改写，后面整段失效。

### 20.5 可执行的工程规则（零成本，但必须守）

按"离开头越近越要稳定"排列：

1. **系统提示 / 长期文档放最前**，且一旦发出永不修改。
2. **绝不编辑已发送的历史消息** —— 要纠正就追加一条，别改旧的。
3. **压缩历史用"追加摘要"，不用"替换历史"** —— 替换会毁掉全部缓存，
   追加只损失 0。这条最重要也最反直觉。
4. **易变内容放最后**：工具输出、当前时间、随机 id、本轮检索结果。
   把它们插在中间会毁掉其后的所有 KV。
5. **多会话共享前缀**用 `--kv-unified-per-slot`（本机构建支持，**尚未实测**）。

### 20.6 一个诚实的外推限制

增量 prefill 并非与上下文长度**完全**无关——新 token 仍要对全部历史做 attention：

| 上下文 | 新增 10 token 的 prompt_ms |
|---|---|
| 439 | 76 ms（7.6 ms/token） |
| 6,734（§18.3） | 223 ms（22.3 ms/token） |

上下文 15.3×，耗时 2.9× —— **亚线性，但不是常数**。
⇒ **30 k 上下文的增量 prefill 未实测**，不要拿 80 ms 去外推。要测就把
`kv_reuse_turns.sh` 的 `ctx_512.txt` 换成长文档再跑一遍。

### 20.7 与 §19 的关系，以及真正的出路

§19 说"AI 每轮失忆"；本节说：只要不改写前缀，**失忆是可以治的，而且已经治了 98%**。
剩下 2% 治不了的部分（必须改前缀的场景）指向同一件事：

**把知识移出上下文。** 进了上下文的东西才要付 prefill；放在外部记忆里
（检索、索引、结构化摘要）的东西，一遍都不用读。这才是根治，而不是把
prefill 从 80 ms 压到 40 ms。

## 21. 把 §20 的四条规则做成程序机制：先验证基石，再发现一个引擎能力的边界

### 21.1 要做的事

§20.5 给了四条零成本但必须守的规则（系统提示锁死 / 不编辑历史 / 压缩用追加不用替换 /
易变内容放末尾）和一条根治方向（把知识移出上下文）。用户要求：**把它们做成程序机制**。

写码之前先验证基石假设：**"易变内容放末尾"是否真的能保住前缀缓存？** 整个机制都压在
这一条上。脚本 `ctest/kv_layout_test.sh`。

### 21.2 实测：基石成立（4.34×）

上下文切成三区，用 server 的 `/tokenize` 实测真实长度：
`FROZEN=9 / HISTORY=421 / VOLATILE=121`（占比 2% / 76% / 22%）。

| case | cache_n | prompt_n | prompt_ms | 复用率 |
|---|---|---|---|---|
| 1 cold（V 在末尾） | 0 | 560 | 3038 | 0.0% |
| 2 重建 VOLATILE（末尾） | 433 | **127** | 805 | 77.3% |
| 3 再重建一次（末尾） | 433 | **127** | 811 | 77.3% |
| 4 **VOLATILE 移到中间** | 8 | **551** | 3423 | 1.4% |
| 5 回到末尾 | 433 | 127 | 794 | 77.3% |
| 6 再回到末尾 | 433 | 127 | 793 | 77.3% |
| 7 **改 FROZEN 一个词** | 3 | 558 | 3561 | 0.5% |

- **稳态只付 |VOLATILE|=127 token；插到中间要付 551 token = 4.34×。**
- **违规的惩罚是一次性的**：case 5 立刻回到 127，不会持续污染。
- **改 FROZEN 一个词 → 全毁**（cache_n=3）。规则 1 是硬约束，不是建议。

⇒ 基石成立。**"易变内容放末尾"这条规则值得被做成机制**，因为它值 4.34×。

### 21.3 意外发现：引擎已内置位置无关的 KV 复用，但救不了这个场景

翻 `server-context.cpp:3238` 时发现 server 早就实现了**块级 KV 平移复用**：

```cpp
slot.mem.seq_rm (slot.id, head_p, head_c);
slot.mem.seq_add(slot.id, head_c, head_c + n_match, kv_shift);   // 把 KV 块平移到新位置
```

只要在新旧 prompt 里找到一段 **≥ `--cache-reuse N`** 的相同 token，就把缓存里那块 KV
**平移**过去，而不是重算。默认 `n_cache_reuse = 0`（禁用），`--fim-qwen-1.5b-default`
预设用 256。能力本身对本机可用（`llama_kv_cache::get_can_shift()` 对 Qwen3 返回 true）。

**实测它对本场景完全无效**（`ctest/kv_cache_reuse_test.sh`）：

| `--cache-reuse` | END prompt_n | MIDDLE prompt_n | 惩罚 |
|---|---|---|---|
| 0（默认） | 127 | 551 | **4.34×** |
| 256 | 127 | 551 | **4.34×** |

原因在算法的**单指针贪心**（server-context.cpp:3252-3276）：

```cpp
if (n_match >= n_cache_reuse) { ...; head_c += n_match; head_p += n_match; }
else                          { head_c += 1; }        // 失败时只推进 head_c
```

`head_p`（新 prompt 的位置指针）**只在成功时才前进**。我们的违规是"在 FROZEN 之后
**插入**一个新块"，于是 `head_p` 一开始就指向那个新块，而 slot 里根本没有它 →
第一次匹配失败 → `head_p` 永远卡死 → 后面 421 token 的 HISTORY 明明完整存在也复用不上。

⇒ **`--cache-reuse` 只救"块顺序不变、整体平移"（典型是 FIM：前缀+后缀不变、中间改写）**，
**救不了"在前部插入新块"** —— 而这正是 agent 工作流最常见的动作。
⇒ **规则 4 不能靠引擎兜底，必须由调用方保证。这是把它做成机制的核心理由。**

### 21.4 因此机制的落点是调用方，不是引擎

| 层 | 该做什么 | 引擎给不给 |
|---|---|---|
| 引擎 | 增量 decode（LCP） | **已给**，默认开 |
| 引擎 | 块级平移复用（`--cache-reuse`） | 已给，但**覆盖不到插入场景** |
| 引擎 | 跨进程持久化（save/restore） | **已给**（§18.3） |
| **调用方** | **保证 prompt 只追加、易变内容在末尾** | **没有任何东西替你做** ← 要写的就是这个 |

⇒ 机制形态：**一层坐在 llama-server 前面的编排层**，把"组装 prompt"这件事从调用方
手里收走，换成只能走 append 的 API。详见 `specs/prompt-ledger.md`（Spec 04）。

## 22. 反量化效率：q4_k_m 的 58% 不是内核 bug，而是**选错了格式**

### 22.1 问题

§17 发现：无上下文 tg128 @t=12，q4_k_m 只有 f16 的 **58%** 带宽效率，

本节把 9 种量化类型全部拉齐，测速度 + 质量 + 两种 kernel 形态的效率。

### 22.3 发现一：`_0` 系列全面快于 `_K` 系列，而且更快的同时还更小

⇒ **我原本要做的"优化 q4_K 内核"，收益上限就是追平 q4_0（+16%）。

⇒ **零改动立刻可得：换 q5_0，+5% 速度，PPL 从 23.48 降到 21.98。**

### 22.5 发现三：低效不只在 GEMV，prefill 也一样

按字节归一后 prefill 的效率同样只有 24~54%（q8_0 53.5%、q4_k_m 48.6%、q2_k 24.1%）。
⇒ **不是"decode 的 GEMV 形状"问题，是量化内核的每字节成本问题**。
（我第一版脚本把 pp 按"同 FLOPs 理想 1.0"归一，得出 q4_k_m pp_eff=161% 这种荒谬数，
是因为 prefill 也是带宽受限、会复用权重，不是计算受限。已改。）

### 22.6 发现四：模型越大效率越高

| | tg_eff |
|---|---|
| 0.6B q4_k_m | 56.7% |
| 4B q4_k_m | **66.5%** |

每线程工作量随 K 增大而增大 ⇒ **存在固定开销 + 内存级并行度不足的成分**，
不是纯粹的内核指令问题。线程扫描同向印证：q4_k_m 从 t=4→12 只涨 14%，
f16 还能涨 44%（量化模型更早饱和）。

### 22.8 测量方法学：本机漂移 ±6%，单次 `llama-bench` 不可作为结论依据

**踩过的坑**：VNNI=ON 重建后连 f16 都"变慢"了 5.7%。f16 根本没有量化内核，
它变慢只可能是机器状态变了。后续交替 A/B 实测到 f16 锚点在 22.8~35.4 t/s 之间摆动。

更严重的一次：**我自己污染了自己的测量**。`deq_ab.log` rep2R→rep3F 期间我在跑
Python 张量解析，f16 从 35.16 掉到 22.84（**−33%**），那两块数据全部作废。

⇒ **项目规则：任何被测量的东西，测量期间机器上不能跑别的。**

**采用的方法**（脚本 `ctest/deq_ab2.sh` + `ctest/ab_ratio.py`）：

1. 每半个块以 `f16` **首尾各测一次**。f16 没有量化内核，其 t/s 是机器状态的纯探针。
2. 每个量化测量除以**在其时间点上线性插值的 f16 基线**。
3. 正序跑一遍、逆序跑一遍（消掉单调漂移）。
4. 块内 f16 摆幅 > 8% 则整块丢弃——说明污染发生在块**内部**，线性插值救不回来。
   脚本会明确打印 `CONTAMINATED - dropped`。

`deq_ab2.log` 6/6 块全干净，f16 锚点 34.24~35.86（±1.4%）。

"这是个 q4_0 模型"是**假的**。脚本 `ctest/gguf_types.py`

根因在 `src/llama-quant.cpp:472`：

### 22.11 地基级更正 #2：我们**从来不是**带宽受限

这是三天来第二次推翻地基（第一次是 §16 作废"25~31 GB/s 带宽墙"）。
现在作废的是它的替代品。

**判据**：如果 decode 是带宽受限，那么**所有量化类型的实得带宽应该相同**
（都等于机器的 DRAM 上限）。实测：

```
f16  2.000 B/elem -> 41.8 GB/s
q8_0 1.062 B/elem -> 35.3 GB/s
q5_0 0.688 B/elem -> 28.3 GB/s
q4_0 0.562 B/elem -> 27.9 GB/s
q6_K 0.820 B/elem -> 26.8 GB/s
q5_K 0.688 B/elem -> 26.1 GB/s
q4_k_m 0.562 B/elem -> 24.4 GB/s
q3_k_l 0.430 B/elem -> 24.1 GB/s
q2_k 0.328 B/elem -> 22.8 GB/s
```

**22.8 ~ 41.8 GB/s，且几乎严格随 B/elem 单调下降。** 带宽受限不可能长这样——
如果真是带宽卡死，q2_k 该跑 147 t/s（§16 的老预测），它跑 77。

旁证（§22.6 线程扫描）：q4_k_m 从 t=4→12 只涨 14%，f16 还能涨 44%。
**读字节少的反而更早饱和**，与带宽受限的预测正好相反。

⇒ **结论：量化 decode 的瓶颈是"每元素的指令/吞吐成本"，不是 DRAM 带宽。**
字节越少，每个字节要摊的 unpack 指令越多，实得带宽就越低。

⇒ **作废**：屋顶线公式 `tok/s = 有效带宽 / 每 token 字节`。
自 §16 起所有"减字节就能线性提速"的推导都基于此，一律作废。
（§14 的 `-ctv q8_0` 屋顶线预测、§15 的"D 是唯一能破屋顶线的路线"同理。）

⇒ **三个直接推论**：
1. **减字节的收益远小于线性**：lm_head 从 Q6_K 压到 Q4_0 省 10.5% 字节，
   换来的速度增益会明显小于 10.5%。
2. **要提速必须降"每元素指令数"**，不是降字节数。
3. **f16 的 41.8 GB/s 只是"f16 内核能达到多少"，不是机器上限**；机器上限未知且更高。

### 22.12 靶点重定（第二次）

| 候选 | 依据 | 上限 | 结论 |
